## P4 → RTL 开源工具调研

- 交付：`docs/P4转RTL开源工具调研.md`
- 核心结论：GitHub 上**无**活跃维护 + 全 pipeline + 直出可综合 RTL 的开源 P4→RTL 工具。
- 关键事实：
  - `p4lang/p4c` `main` 的 `backends/` 经 GitHub 官方 API 核对 = {bmv2, common, dpdk, ebpf, graphs, p4fmt, p4test, p4tools, tc, tofino, ubpf}，**无 HDL/RTL backend**。
  - 开源侧最近似：`p4fpga/p4fpga`（92★，Bluespec 全流程，2017 停更）；`boutros-lab/patterns-to-parsers`（MIT，2026-06 新建，**只做 parser**，PIR + Jinja2 → SystemVerilog，Waterloo + Meta）。
  - 替代路线：Menshen（6,330 行 Verilog 参数化 RMT pipeline，**固定 RTL + P4 编译成配置**，非 RTL 生成）+ `menshen-open-nic` 移植到 AMD OpenNIC。
  - 工业可用全部闭源：AMD VitisNetP4（P4 → 模板化 C++ → Vitis HLS）、Intel/Altera P4 Suite for FPGA（2025 新出，真·P4→RTL 直出）。
- ⚠️ 数据可信度坑：大量镜像/SEO 站（onlybits.org、ghub.com、git-hub.com、arcxiv.org 等）转载的 p4c README 含 `p4c-apollo-tuna` backend 等描述，**经官方 API 核对为假**，GitHub 上也查不到 `tuna_nic`/`tunic` 仓库。后续同类调研务必用 `api.github.com/repos/<o>/<r>/contents/` 直接验证，不要信搜索摘要。
- 缺口（若自研的机会点）：Match-Action 单元的开源 RTL 生成（TCAM/LPM/EM 表映射）目前**完全没有**公开件；ALU/流水级资源分配调度（CaT 有算法未开源）。

## 拉取 google/xls 到本地

- 路径：`third_party/xls/`，来源 `google/xls@49c163e`（main，2026-09-11），155 MB，完整历史 10,677 commits，fsck 干净。
- 方式：`gh.monlor.com` 镜像走 git 智能 HTTP，浅克隆 + `--unshallow`，全程 ~53s（峰值 ~4.4 MB/s）。
- 关键事实：XLS 依赖走 **Bzlmod**（`MODULE.bazel`，45 个 bazel_dep），**无 git submodule**，依赖在构建时由 Bazel 拉取。Bazel 版本要求 8.7.0。
- 备用安装：conda 有预编译包 `conda install -c litex-hub xls`，可跳过重量级自建。
- 记录文件：`docs/third-party-xls.md`（含更新命令、构建入口、与 P4→RTL 的关系）。
- 关联：XLS 可作 P4→RTL 的后端候选（P4 IR → XLS IR/DSLX → codegen → Verilog），省掉自研 RTL 生成器，代价是语义映射工作量。

## p4c 扩展 XLS 后端的方案设计

- 交付：`docs/p4c-xls后端扩展方案.md`（含实施链路图）
- 核对到的 XLS 侧硬事实（读本地源码，非搜索）：
  - IR 只有 **79 个 op**（`xls/ir/op_list.h`），全量清单已抄进文档；**无任何存储器/CAM 原语**。
  - `docs_src/dslx_std.md` **无 ram 原语**；RAM 只存在于低层 IR pass（`xls/ir/ram_rewrite.proto`：`RAM_ABSTRACT/1RW/1R1W`）。
  - proc → Verilog **有正式测试**（`xls/codegen_v_1_5/codegen_proc_test.cc`），且 codegen_v_1_5 有 `pipeline_register_insertion_pass` / `flow_control_insertion_pass` / `scheduling_pass` → proc+state 可直接综合成带 ready/valid 的流水 RTL。
  - DSLX 语法确认：`proc { config / init / next(state) }` + `chan<T>` + `send/recv/join` + `spawn`，`config` 是编译期 elaboration。
- p4c 侧事实：`backends/` = {bmv2, common, dpdk, ebpf, graphs, p4fmt, p4test, p4tools, tc, tofino, ubpf}；`Backend` 基类契约只有一个纯虚函数 `virtual void convert(const IR::ToplevelBlock*)`（定义在 `backends/bmv2/common/backend.h`）。新增后端 = `backends/<name>/CMakeLists.txt` + `driver/p4c.<name>.cfg` + 在 `backends/CMakeLists.txt` 加 `add_subdirectory`。
- 方案要点（三条最大判断）：
  1. 后端骨架只占约 **10%** 工作量；90% 在语义映射（DSLX 生成器，≈40 条映射规则）。
  2. **最大阻塞 = table 无处落脚**：XLS 无存储原语，TCAM/LPM 匹配逻辑必须自研 RTL，XLS 侧只能留接口。
  3. 推荐**路线 C**：p4c 只做 frontend+midend 输出 **PIR JSON**，DSLX 生成器用 Python(Jinja2) 写 → 与 p4c 解耦，PIR 可复用到其他 RTL 后端。
- 第二阻塞：XLS 调度器按 delay model 自由优化，产出的流水级数与 PISA 的"一表一 stage"不对齐，需自研 stage 分配 pass 或用 `--pipeline_stages` 硬约束。
- 量级估算：跑通 MVP 7–11 人月；接近可用 15–22 人月。
- 定位建议：XLS 适合低吞吐路径/控制面辅助逻辑/功能原型；**核心线速流水线风险高**（通用数据流调度器 vs 网络芯片结构化 TCAM/ALU 阵列）。
- 验证策略：三级对拍（bmv2 golden / XLS JIT·解释器 / iverilog 仿真）+ p4c `testdata/p4_16_samples` 回归 + XLS `solvers`(Z3) 做 LEC。
