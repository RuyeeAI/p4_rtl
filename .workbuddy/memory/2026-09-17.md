## 内嵌 IR 静态校验器（A0 门禁）补全 proc/数组 state ✅

需求（郝宇）：修掉 `xls_ir_lint.py` 对 proc / 数组 state 覆盖滞后，并重新发布流程。

**修复前**：lint 只实现 `fn` 形态，把 proc 体内节点行当顶层语句 →
对真 XLS parser 完全接受的 IR 报 **8262 条** issue（demo9），流程里只能降级 WARN。

**做法**：不再"猜语法"，全部对照 `third_party/xls` 真实源码逐条实现，注释里标出处
（`ir_parser.cc:2168` ParseProcSignature / `:2986` ParseChannelInterface / `:2754` ParseChannel /
`:461` ParseAndResolveIdentifier / `:1524,1533` 节点名-id 一致性 / `:1486` 重名豁免 /
`channel.cc:158,202,285,304` 枚举 / `ir_scanner.cc:180` 三引号字符串）。

**补的语义检查（原来完全没有）**
- 先定义后引用（含 state_element= / channel= 的存在性）
- 节点名 `.<N>` 后缀必须等于 op 名与 `id=N`
- 重名判据（Param / StateRead 豁免）、名字作用域按 fn/proc 隔离
- `init` 初值个数 == state 数；`next_value` 的 param/state_element 二选一；重复关键字

**连带修掉契约表缺陷**：`gen_op_contracts.py` 用 `to_snake(C++ 名)` 挂键，与 `op_list.h` 的
**IR 文本 op 名**不总相等（`kNext` → IR 名是 `next_value` 而非 `next`），导致 `next_value` 落到
"无 case"分支被补成**空契约** → 合法 IR 报一片 `E_UNKNOWN_KW`。现按 op_list.h 重映射
（5 条：next_value / smul / smulp / umul / umulp）。

**门禁可信度（关键证据）**
- 新增 `scripts/xls_ir_lint_selftest.py`：33 个错误用例 + 9 个正向控制 → **42/42 通过**
  （证明不是"恒过"）。
- 官方 XLS 全树 `.ir` → **768/768 通过**（A1 用真 XLS parser 测的是 745/768）。
- 本仓库 `testcases/ir/**` → **25/25**，0 issue。
- 反向验证：往 demo9 的 IR 注入 3 处真错（漏 init 初值 / 节点名改坏 / 引用未定义名字）
  → 逐条报出且带行号。

**流程侧**
- lint 从"降级 WARN"恢复为**真门禁（报错即 FAIL）**（`Flow.stepLint`）。
- 6 样本回归：exit=0 / 0 FAIL / lint 通过 / 形式验证 0 未决 / 仿真全通过。
- **发布形态修掉一个洞**：`p4xls lint-ir` 原来只在 cwd 有 `scripts/` 时可用，
  现在与 `flow` 共用"仓库 scripts/ 优先 → jar 内嵌资源解到临时目录"的回退并自带 `--contracts`；
  实测 **单 jar + 空 root** 下 `lint-ir` 可用且能正确拦错。

**踩坑**
- `to_snake("kNext")` = `k_next` —— 忘了剥枚举名的 `k` 前缀，导致重映射分支永不命中。
- `scheduled_block` 的体内内嵌 `source fn` 声明，"跳到下一个顶层关键字"会被它骗到 →
  必须跳过签名后**按花括号配对**整段跳（14 个官方样本曾因此各报上千条 E_TOP）。
- `id=` / `pos=[...]` 是**类型参数**的尾随属性（`ir_parser.cc:134-138`），不是 proc 签名的
  关键字参数；`pos=[(0,8,6)]` 出现在 `__state: () pos=...` 这种位置。
