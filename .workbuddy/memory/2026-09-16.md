## P0 ✅ II 编排水法定案（同日晚）

**定案：并行 token 拓扑（通道操作不串链）→ 最小 II 从 2 降到 1。**

实验设计：四个变体只改 token 拓扑，其余（FSM/通道/predicate）不变；
用 `scripts/ii_sweep.sh` 做 stages × wct 矩阵扫描，**最小的能成功的 wct 即最小 II**。

| 变体 | 最小 II |
|---|---|
| B1 只有 send | 1 |
| B2 只有 receive | 1 |
| **B3 并行 token**（都直连 state_read(tok)，末尾 after_all 汇聚） | **1** |
| B4 基线 串行 token 链 | 2（stages=1 时完全不可调度） |

**推导**：B1/B2 都是 1 → **瓶颈不是通道操作本身**；
B3=1 而 B4=2，两者只差 token 拓扑 → **瓶颈是 token 串链形成的循环携带依赖**。

**收益**（功能不变的前提下）：
- 吞吐翻倍（II 2→1，即一拍一迭代）；
- 端到端延迟**少 1 拍**（等 2 拍→result 第 3 拍，等 7 拍→第 8 拍）；
- RTL 寄存器 **9 → 4 个**，规模 3812 → **2474 字节（−35%）**。

**II 的表达方式定为写进 IR**：`#[initiation_interval(1)]`。
实测该属性现在可用（`:passes` 修复后），生成物与 `--wct=1` **完全一致**。
好处：生成的 `.ir` 自描述，不依赖我们 driver 的调用约定。
坑：若同时给 `--wct=N`，**命令行选项优先**于属性。

**⚠️ 给 A2 生成器的关键约束（最容易出事的地方）**：
拆 token 链的正确性**完全依赖 predicate 互斥**。生成器必须证明同 proc 内
各通道操作的 predicate 互斥（如由同一个 FSM 相位派生）；
**证明不了就必须退化为串行链（接受 II=2）并显式报诊断** ——
静默拆链会产出"能编译、能过仿真、但真实硬件行为不确定"的 RTL。

**testbench 新增 case 3（背压）**：`key_out_rdy` / `result_out_rdy` 为 0 期间
不得发生传输，放开后数据完好 → 通过。这条是接口契约的一部分（A3 要用）。

**遗留**：多通道 / 多表在同一 proc 内的 II **未验证** —— A3 第一个检查点就扫。

## M0 阶段的 6 个必须记住的坑（详见报告 §3）

### K3 是最坑的一个 —— 缺 `//xls/codegen_v_1_5:passes`

症状：`default_pipeline is not registered. Have [..., opt_pass<default_pipeline>, ...]`

两个误导点：
1. 报错列表里**明明有** `opt_pass<default_pipeline>` → 以为注册表没问题。
   实际 `GetCodegenPassRegistry()` 是**独立于优化 pass 注册表**的另一张表。
2. **该错误只在"调度成功之后"才出现**。调度失败时先报 `cannot achieve full throughput`，
   于是极易误判成调度问题，反复调 `--stages`/`--wct`（我在这里绕了很久）。

正解：官方 `xls/tools/BUILD:845` 里 `//xls/tools:codegen` 显式依赖
`//xls/codegen_v_1_5:passes`，而 `//xls/codegen_v_1_5:codegen` 的 deps 里**没有**它。
自建 driver 补上即解。

> **教训**：自建 driver 时必须把「官方 main 的 deps」逐个对照一遍，
> 尤其是注册表/插件式的 alwayslink 依赖 —— 它们不体现在任何 API 上。

**快速判定法**：拿官方自带的最小 proc 样本
（`xls/ir/testdata/ir_parser_round_trip_test_ParseIIProc.ir`）跑同一个 driver，
能复现说明是工具链问题、不是自己的 IR 问题。

### K1 —— 「token 链 + 阻塞通道」的 proc 拿不到 II=1

源码依据 `xls/scheduling/run_pipeline_schedule.cc:232-242`：
可达最小 WCT = max over state of (cycle[next] − cycle[state_read] + 1)。
token 回边 `read(tok) → send → receive → send → next(tok)` 跨多拍 → II=1 不可达。
**实测 `--wct=2` 后调度通过并成功出 Verilog。**

→ **对 PISA「一拍一包」是硬约束**，A2 编排水法必须先决策（报告 §5.1 给了三个候选：
拆 proc / 接受 II=2 / 不把 token 写回 state）。

### K2 —— `worst_case_throughput` 语义反直觉

`run_pipeline_schedule.cc:456-463`：**0 = 不约束**；**不设 = 必须为 1**；N = 必须为 N。

### K4 —— `clock_name` 必填

`scheduled_block_conversion_pass.cc:56-61` 检查 `options.clock_name()`。
官方 `codegen_main` 靠 flag handler registry 填默认值，自建 driver 必须显式设。

### K5 —— proc-scoped `chan_interface` 的 `strictness` 必填

老式顶层 `chan` 不写时默认 `proven_mutually_exclusive`（`ir_parser.cc:2964`），
proc-scoped 走 `SetStrictness(optional)` → 缺省即 nullopt → `verifier.cc:384` 校验不过。

### K6 —— IR 文本两条硬规则

1. 节点名 `<op>.<N>` 的后缀 N **必须等于** `id=` 属性值
2. 引用必须先于定义

## 对 A3 接口规范的一条直接影响

**XLS 生成的 `rsp_in_rdy` 语义是「本拍完成一次接收」，不是「我随时能收」。**
无数据时（WAIT + `rsp_in_vld=0`）rdy 也是 0。协议仍合法（vld&rdy 同拍=一次传输），
但**外部存储器/表接口不能把 rdy 当"可以发数据"的许可**——
必须写进 A3 规范：由 XLS 侧决定何时接收，外部只在数据就绪时拉 vld 并保持。

## 运维纪律（代价 22 分钟）

**不要 kill 正在跑的 Bazel 构建。** 被 SIGTERM 的客户端会在 server 侧留下悬挂命令锁
（`Another command (pid=...) is running`，而该 pid 已不存在）；
此时 `kill -9` server 会让在飞动作作废 → 全量重编（实测 22 分钟）。
增量正常 10 秒 ~ 4 分钟；首次全量 25 分钟 / 5093 actions。

## 接口裁剪：删除 Key/Response 的 rdy（郝宇 2026-09-16 晨）

**要求**：删掉 `out/m0/m0_key_rsp_loop.v` 里的 `rsp_in_rdy` 与 `key_out_rdy` 接口及相关逻辑。
按字面只删这两个（`result_out_rdy` 保留）。

**做法（关键）**：**不手改生成物**，而是改 IR 源再重新生成。手改 .v 会被下次
重新生成覆盖，且与源不一致。

XLS 的 `FlowControl` 枚举其实有**三**个值（`channel.h:301-320`），
我此前只看到两个：

| 值 | 语义 | 端口 |
|---|---|---|
| `kNone` | 无流控，靠外部机制保证不丢 | 只有 `<chan>` |
| `kReadyValid` | ready+valid 握手 | `<chan>` / `_vld` / `_rdy` |
| **`kValidData`** | **只有 valid，接收方假定永远 ready（不支持背压）** | `<chan>` / `_vld` |

→ IR 文本写 `flow_control=valid_data` 即精确得到"保留 vld、去掉 rdy"。
依据 `channel_to_port_io_lowering_pass.cc:371`：
`if (ChannelRefFlowControl(channel) != FlowControl::kValidData) { 加 rdy 端口 }`。

### 最需要记住的结论：stall 与握手协议正交

改之前有一个**必须实测**的风险：`valid_data` 下没有 rdy 可供 proc 反向表达
「我没准备好」—— **XLS 是否因此不再 stall，从而破坏「等 response 返回」的契约？**

**实测：不会破坏。** case 1/2 在等待期内逐拍断言 `result_out_vld == 0` 全通过，
延迟完全没变（第 3 拍 / 第 8 拍）。

RTL 里看得很清楚：stall 链是
`rsp_in_vld=0 → active_inputs_valid_1=0 → stage_outputs_valid_1=0 →
p1_stage_done=0 → stage_outputs_ready_0=0 → state 全部保持`，
**整条链里没有任何 rdy 信号**。

→ **"等待"是 proc 内部的流水控制，与外部 ready/valid 协议是两件独立的事。**

### 结果

| | 改前 | 改后 |
|---|---|---|
| 端口 | key_out_rdy / rsp_in_rdy 存在 | **已删除** |
| RTL 字节 | 2474 | **2346** |
| II / 端到端延迟 | 1 / 第3、8 拍 | **不变** |
| `active_outputs_ready_1` | `(key_out_rdy \| ~is_idle) & (result_out_rdy \| ~is_disp)` | `result_out_rdy \| ~is_disp` |

### 代价（必须写进 A3 接口规范）

`valid_data` 的约定是"receiver is presumed to always be ready"，
所以 XLS 侧**不再有任何机制通知外部"请缓冲"**：
- `key_out`：外部被约定**随时可接收**；有不可用窗口就得外部自己加 FIFO
- `rsp_in`：外部被约定**随时会返回**，XLS 侧不表达"能否接收"

即**风险从"协议复杂"转移到"外部必须保证不丢"**。将来若外部难以满足
（例如表查访会长时间阻塞），把该通道改回 `ready_valid` 即可 ——
改动只是 IR 里一个词，两版都实测通过。

### 附带收益

改回 `ready_valid` 时需注意的坑仍在：XLS 的 `rsp_in_rdy` 语义是
「本拍完成一次接收」而非「我随时能收」。用 `valid_data` 后这个歧义根本不存在了。
