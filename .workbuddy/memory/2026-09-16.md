## P0 ✅ II 编排水法定案（同日晚）

**定案：并行 token 拓扑（通道操作不串链）→ 最小 II 从 2 降到 1。**

实验设计：四个变体只改 token 拓扑，其余（FSM/通道/predicate）不变；
用 `scripts/ii_sweep.sh` 做 stages × wct 矩阵扫描，**最小的能成功的 wct 即最小 II**。

| 变体 | 最小 II |
|---|---|
| B1 只有 send | 1 |
| B2 只有 receive | 1 |
| **B3 并行 token**（都直连 state_read(tok)，末尾 after_all 汇聚） | **1** |
| B4 基线 串行 token 链 | 2（stages=1 时完全不可调度） |

**推导**：B1/B2 都是 1 → **瓶颈不是通道操作本身**；
B3=1 而 B4=2，两者只差 token 拓扑 → **瓶颈是 token 串链形成的循环携带依赖**。

**收益**（功能不变的前提下）：
- 吞吐翻倍（II 2→1，即一拍一迭代）；
- 端到端延迟**少 1 拍**（等 2 拍→result 第 3 拍，等 7 拍→第 8 拍）；
- RTL 寄存器 **9 → 4 个**，规模 3812 → **2474 字节（−35%）**。

**II 的表达方式定为写进 IR**：`#[initiation_interval(1)]`。
实测该属性现在可用（`:passes` 修复后），生成物与 `--wct=1` **完全一致**。
好处：生成的 `.ir` 自描述，不依赖我们 driver 的调用约定。
坑：若同时给 `--wct=N`，**命令行选项优先**于属性。

**⚠️ 给 A2 生成器的关键约束（最容易出事的地方）**：
拆 token 链的正确性**完全依赖 predicate 互斥**。生成器必须证明同 proc 内
各通道操作的 predicate 互斥（如由同一个 FSM 相位派生）；
**证明不了就必须退化为串行链（接受 II=2）并显式报诊断** ——
静默拆链会产出"能编译、能过仿真、但真实硬件行为不确定"的 RTL。

**testbench 新增 case 3（背压）**：`key_out_rdy` / `result_out_rdy` 为 0 期间
不得发生传输，放开后数据完好 → 通过。这条是接口契约的一部分（A3 要用）。

**遗留**：多通道 / 多表在同一 proc 内的 II **未验证** —— A3 第一个检查点就扫。

## M0 阶段的 6 个必须记住的坑（详见报告 §3）

### K3 是最坑的一个 —— 缺 `//xls/codegen_v_1_5:passes`

症状：`default_pipeline is not registered. Have [..., opt_pass<default_pipeline>, ...]`

两个误导点：
1. 报错列表里**明明有** `opt_pass<default_pipeline>` → 以为注册表没问题。
   实际 `GetCodegenPassRegistry()` 是**独立于优化 pass 注册表**的另一张表。
2. **该错误只在"调度成功之后"才出现**。调度失败时先报 `cannot achieve full throughput`，
   于是极易误判成调度问题，反复调 `--stages`/`--wct`（我在这里绕了很久）。

正解：官方 `xls/tools/BUILD:845` 里 `//xls/tools:codegen` 显式依赖
`//xls/codegen_v_1_5:passes`，而 `//xls/codegen_v_1_5:codegen` 的 deps 里**没有**它。
自建 driver 补上即解。

> **教训**：自建 driver 时必须把「官方 main 的 deps」逐个对照一遍，
> 尤其是注册表/插件式的 alwayslink 依赖 —— 它们不体现在任何 API 上。

**快速判定法**：拿官方自带的最小 proc 样本
（`xls/ir/testdata/ir_parser_round_trip_test_ParseIIProc.ir`）跑同一个 driver，
能复现说明是工具链问题、不是自己的 IR 问题。

### K1 —— 「token 链 + 阻塞通道」的 proc 拿不到 II=1

源码依据 `xls/scheduling/run_pipeline_schedule.cc:232-242`：
可达最小 WCT = max over state of (cycle[next] − cycle[state_read] + 1)。
token 回边 `read(tok) → send → receive → send → next(tok)` 跨多拍 → II=1 不可达。
**实测 `--wct=2` 后调度通过并成功出 Verilog。**

→ **对 PISA「一拍一包」是硬约束**，A2 编排水法必须先决策（报告 §5.1 给了三个候选：
拆 proc / 接受 II=2 / 不把 token 写回 state）。

### K2 —— `worst_case_throughput` 语义反直觉

`run_pipeline_schedule.cc:456-463`：**0 = 不约束**；**不设 = 必须为 1**；N = 必须为 N。

### K4 —— `clock_name` 必填

`scheduled_block_conversion_pass.cc:56-61` 检查 `options.clock_name()`。
官方 `codegen_main` 靠 flag handler registry 填默认值，自建 driver 必须显式设。

### K5 —— proc-scoped `chan_interface` 的 `strictness` 必填

老式顶层 `chan` 不写时默认 `proven_mutually_exclusive`（`ir_parser.cc:2964`），
proc-scoped 走 `SetStrictness(optional)` → 缺省即 nullopt → `verifier.cc:384` 校验不过。

### K6 —— IR 文本两条硬规则

1. 节点名 `<op>.<N>` 的后缀 N **必须等于** `id=` 属性值
2. 引用必须先于定义

## 对 A3 接口规范的一条直接影响

**XLS 生成的 `rsp_in_rdy` 语义是「本拍完成一次接收」，不是「我随时能收」。**
无数据时（WAIT + `rsp_in_vld=0`）rdy 也是 0。协议仍合法（vld&rdy 同拍=一次传输），
但**外部存储器/表接口不能把 rdy 当"可以发数据"的许可**——
必须写进 A3 规范：由 XLS 侧决定何时接收，外部只在数据就绪时拉 vld 并保持。

## 运维纪律（代价 22 分钟）

**不要 kill 正在跑的 Bazel 构建。** 被 SIGTERM 的客户端会在 server 侧留下悬挂命令锁
（`Another command (pid=...) is running`，而该 pid 已不存在）；
此时 `kill -9` server 会让在飞动作作废 → 全量重编（实测 22 分钟）。
增量正常 10 秒 ~ 4 分钟；首次全量 25 分钟 / 5093 actions。

## 接口裁剪：删除 Key/Response 的 rdy（郝宇 2026-09-16 晨）

**要求**：删掉 `out/m0/m0_key_rsp_loop.v` 里的 `rsp_in_rdy` 与 `key_out_rdy` 接口及相关逻辑。
按字面只删这两个（`result_out_rdy` 保留）。

**做法（关键）**：**不手改生成物**，而是改 IR 源再重新生成。手改 .v 会被下次
重新生成覆盖，且与源不一致。

XLS 的 `FlowControl` 枚举其实有**三**个值（`channel.h:301-320`），
我此前只看到两个：

| 值 | 语义 | 端口 |
|---|---|---|
| `kNone` | 无流控，靠外部机制保证不丢 | 只有 `<chan>` |
| `kReadyValid` | ready+valid 握手 | `<chan>` / `_vld` / `_rdy` |
| **`kValidData`** | **只有 valid，接收方假定永远 ready（不支持背压）** | `<chan>` / `_vld` |

→ IR 文本写 `flow_control=valid_data` 即精确得到"保留 vld、去掉 rdy"。
依据 `channel_to_port_io_lowering_pass.cc:371`：
`if (ChannelRefFlowControl(channel) != FlowControl::kValidData) { 加 rdy 端口 }`。

### 最需要记住的结论：stall 与握手协议正交

改之前有一个**必须实测**的风险：`valid_data` 下没有 rdy 可供 proc 反向表达
「我没准备好」—— **XLS 是否因此不再 stall，从而破坏「等 response 返回」的契约？**

**实测：不会破坏。** case 1/2 在等待期内逐拍断言 `result_out_vld == 0` 全通过，
延迟完全没变（第 3 拍 / 第 8 拍）。

RTL 里看得很清楚：stall 链是
`rsp_in_vld=0 → active_inputs_valid_1=0 → stage_outputs_valid_1=0 →
p1_stage_done=0 → stage_outputs_ready_0=0 → state 全部保持`，
**整条链里没有任何 rdy 信号**。

→ **"等待"是 proc 内部的流水控制，与外部 ready/valid 协议是两件独立的事。**

### 结果

| | 改前 | 改后 |
|---|---|---|
| 端口 | key_out_rdy / rsp_in_rdy 存在 | **已删除** |
| RTL 字节 | 2474 | **2346** |
| II / 端到端延迟 | 1 / 第3、8 拍 | **不变** |
| `active_outputs_ready_1` | `(key_out_rdy \| ~is_idle) & (result_out_rdy \| ~is_disp)` | `result_out_rdy \| ~is_disp` |

### 代价（必须写进 A3 接口规范）

`valid_data` 的约定是"receiver is presumed to always be ready"，
所以 XLS 侧**不再有任何机制通知外部"请缓冲"**：
- `key_out`：外部被约定**随时可接收**；有不可用窗口就得外部自己加 FIFO
- `rsp_in`：外部被约定**随时会返回**，XLS 侧不表达"能否接收"

即**风险从"协议复杂"转移到"外部必须保证不丢"**。将来若外部难以满足
（例如表查访会长时间阻塞），把该通道改回 `ready_valid` 即可 ——
改动只是 IR 里一个词，两版都实测通过。

### 附带收益

改回 `ready_valid` 时需注意的坑仍在：XLS 的 `rsp_in_rdy` 语义是
「本拍完成一次接收」而非「我随时能收」。用 `valid_data` 后这个歧义根本不存在了。

### A2-0 前置实验（两个，都决定架构，不做就要返工）

**实验一：多通道/多表的 II（P0 遗留事项）**

`scripts/gen_multichan_probe.py N` 生成「N 张表争用同一 proc」探针
（每表 2 相位 + 1 dispatch = 2N+1 相位、2N+1 通道；通道操作都直连
state_read(tok)、互不串链、predicate 互斥、末尾 after_all 汇聚）。

| N | 2 | 3 | 4 | 6 | 8 |
|---|---|---|---|---|---|
| 通道数 | 5 | 7 | 9 | 13 | 17 |
| 最小 II | **1** | **1** | **1** | **1** | **1** |

→ **通道数量不是 II 的瓶颈，整个 control 可以放进一个 proc。**

⚠️ 踩坑：首次跑 N=3/4 全失败（`Invalid parameter keyword argument \`init\``），
一度以为是 XLS 的通道数限制，**实际是生成器 bug**：`",\n".join(state_params)`
的最后一个形参没逗号，后面紧跟 `init={...}` 就缺了分隔符。
**"手写 2 表能过、生成的不能过"这个对比才把问题指向生成器。**
→ 教训：用生成器做实验前，先用**手写样本**跑通同一结构作对照。

**实验二：proc 内 invoke（复用现有 action 生成器的前提）**

`testcases/a2/probe_proc_invoke.ir` 实测通过 → `out/a2/probe_proc_invoke.v`
（fn 被内联展开：`assign res = data_in + one`）。

两条硬规则（都是踩坑得来）：
1. **invoke 返回类型 = 被调函数的返回类型**。纯数据 fn 直接返回其值；
   只有接受 token 形参的 fn 才返回 `(token, ...)`。
   错写成 `(token, bits[32]) = invoke(...)` 调纯 fn →
   `Declared type (token, bits[32]) does not match expected type bits[32]`。
   官方两处带 token 的 invoke 样本，被调函数名都带 `__itok__` 前缀。
2. **节点 id 必须 package 级全局唯一**（不是每个 fn/proc 各自从 1 编）。
   fn 用 1..2、proc 也从 1 开始 → `ID 1 is not unique`。

### 架构定案（docs/A2-架构设计.md）

- **一个 P4 程序 → 一个 proc**（parser FSM + control FSM 合一）。
  跨 proc 互连需要 package 级 `chan` 声明 + 绑定（**尚未验证**），
  而单 proc 是已验证形态。代价是 proc 较大。
- PHV 扁平化成 `bits[K]`，编译期定字段偏移 + 每个 header 一个 valid 位。
- action → `fn`（复用 IrText.dump），proc 用 invoke 调用。
- 每张 runtime 表一对 key_out/rsp_in 走 valid_data（无背压，见接口裁剪）。
- id 用全局单调计数器。

## A2-2 + A2-3 ✅：XlsBackend（parser → proc）与 demo3 端到端

### XlsBackend 的映射设计（新增 src/main/scala/P4C/XlsBackend.scala）

- **每个 header 一对 state**：`h_<inst>` 存数据、`v_<inst>` 存 valid。
  不拼一个大的 `bits[K]` PHV —— extract 只更新对应 header，拆开就不必
  反复对整个 PHV 做 concat/bit_slice；输出时再拼（demo3 拼成 274 位）。
- **相位编码**：`0..N-1` = parser 状态（按声明序），`N` = accept，`N+1` = reject；
  accept/reject 处理完回相位 0 重新收包。复位值 0 天然落在 start。
- **通道**：`pkt_in`(receive, 512b) + `phv_out`(send)。通道操作都接同一个
  `state_read(tok)`（P0 定案），末尾 after_all 汇聚。
- **select** 用倒序嵌套 `sel` 实现（先声明的 case 优先级高）。
- **复用** `ChiselBackend.layoutParser` 的字节偏移计算（避免两份漂移）：
  把 `StateLayout` 与 `layoutParser` 从 `private` 放宽到 `private[P4C]`。
  放宽可见性不改变行为，Chisel 线不受影响。
- 范围：第一版**只有 parser**，遇到 control 报明确诊断。

### 两个新踩的坑

1. **`sel` 的 default 规则**：XLS 不允许「cases 已覆盖 selector 全部取值」时
   出现 default（`Select has useless default value: selector has N bits with M cases`）。
   生成器里 12 处 sel **有 6 处踩中** —— 凡以 `bits[1]` 谓词为 selector 的
   「旧值/新值」二选一都是 2^1 = 2 个 case。
   **修法不是逐个调用点手工判断，而是让工具承担**：`XlsProc.Builder` 现在记录
   每个节点的类型（`defined: 名字 → 类型`），`sel` 按 selector 位宽自动判断并
   省略 default。调用方不必再关心这条规则。
2. **`expect` 在 `iverilog -g2012` 下是保留字**（SystemVerilog 断言关键字）。
   用作 testbench 变量名会报一堆指向声明行的莫名语法错。改名即可。

### 决策修正：action 不用 `fn` + invoke，改为**内联进 proc**

原方案（docs §3.4）是 action 的 Dag → `fn`，proc 里 `invoke` 它（A2-0 §2 已实测
invoke 可用）。落地时改成内联，理由：

| | invoke `fn` | 内联（选定） |
|---|---|---|
| 复用收益 | 无 —— 实测 XLS **对 invoke 也是内联展开** | 同左 |
| fn 形参/返回值如何对接 proc 的 state | **未验证** | 不需要：`Ir.InputRef` 直接落到 state 读节点 |
| 额外语法要求 | 须满足 invoke 返回类型规则 | 无 |

内联没有丢掉复用：action 的 body 仍走 Chisel 线的 `IrBuilder.ExprLowering`
（宽度推断 / fit / 运算符映射一份实现）→ `Passes.runAll` → 逐节点映射到
`XlsProc.Builder`。这张映射表与 `IrText.dump` 是同一张：
`Const→literal`、`Zext→zero_ext`、`Trunc/Slice→bit_slice`、`Cat→concat`、
`Mux→sel(cases=[假,真])`、`Not→not`、`Bin→add/…`。

> `XlsProc.Builder` 为此补了两个算子：`zeroExt`、`notNode`（`not` 与 IrText
> 口径一致，**不带 `id=`**，但名字仍用 id 后缀保证唯一）。

### control 的 proc 布局（`XlsBackend.emitControl`）

- **字段级 state**（`<param>_<member>[_<field>]`），不是 header 级。
  control 的 action 是局部修改（`meta.cls = c`），字段级让「改哪个就更新哪个」
  成为最直接的写法 —— 不必把整个 header 拆开再拼回去。
- **相位**：`0` 收 PHV（`phv_in` 拆成各字段 `bit_slice`）→ `1..S` apply 体
  每条语句一拍 → `S+1` 发 PHV（各字段 `concat` 回去）→ 回 0 重新收包。
- **PHV 布局** = control 参数展平序（params 按声明序 → struct 成员按声明序 →
  header 字段按声明序），先声明者在**高位**，与 `concat` 左=MSB 一致。
  demo2 实测 136 位：`dstAddr(48) | srcAddr(48) | etherType(16) |
  normPort(16) | cls(8)`，etherType 落在 `[39:24]`。
- **const 表编译期内联**：
  - 逐表项算 `hit_i`：逐 key 元素 `eq` 后 `and`（与整体 `concat` 后比较等价，
    但避免了拼接宽度的边界坑）；
  - 每条表项输出 action 的候选值（参数是常量，XLS 折叠掉）；
  - 按**声明序优先**倒序嵌套 `sel` 选出；`default` 表项的输出作基线（优先级最低）；
  - 只对「有任一表项写出」的字段做选择 —— 没被写的字段保持原值（正确语义）。
- **每条语句一个相位** ⇒ 相位互斥，字段的 next 值 = 逐相位 `sel` 链，
  天然实现「后写的覆盖先写的」。

### 做法：`emitParser` + `emitControl` 统一重写成 `emitPipeline`

没有保留两套（虽然合并样本可以直接复用旧函数），因为**三份代码必然漂移**。
统一后的口径：

- **字段级 state**（`<inst>_<field>` / `<inst>_v` / `md_<member>`）成为 parser 与
  control 的共同表示 —— parser 的 extract 本来就是按字段切片，control 的 action
  本来就是局部修改，两者在字段级天然对齐。
- **PHV 输出布局统一**：header 按声明序拼 `(valid, 字段…)`，再拼 meta，先声明者在高位。
  demo3 的 274 位输出**不变**（原来就是 (valid,data)*），demo2 从 136 → 137 位
  （多了 valid 位）—— TB 同步更新。
- **相位编码统一**（P = parser 主状态数，S = apply 语句数）：
  `0..P-1` parser（相位 0 兼收包）→ `ctrlBase..+S-1` control（ctrlBase = P>0 ? P : 1）
  → `phSend` 发 PHV → 回 0。`accept → ctrlBase`，`reject → phSend`（不再有独立的
  accept/reject 相位）。无 parser 时相位 0 专用于收 PHV，与 A2-4 完全一致。

### 真 bug：valid=0 的 header 数据跨包残留

首跑 case 2/3 失败：ipv4 的**数据字段**残留上一包的值（`4500003c...`）——
我只在相位 0 清了 valid 和 meta，没清 header 数据字段。

**修法**：相位 0 清**所有**槽位（含 header 数据）。理由：valid=0 时数据本无意义，
但清零让输出**确定**，下游与验证都能依赖；代价是每字段一个 mux。
**教训**：state 是持久的，FSM 回到起点 ≠ 数据回到起点；**每包开始处显式重置**，
否则残留会顺着"保持原值"的 sel 链一路流下去。

### 前置实验（探针 `testcases/a2/probe_state_array{,2}.ir`）—— §6 定案

1. **数组 state 完全可行**：`mem: bits[16][8]` 合法；RTL 是 `reg [15:0] __mem[0:7]`
   寄存器组、索引读 `__mem[idx]`。
2. **init 的数组字面量 = `[元素,...]`，不带类型前缀** —— 写 `bits[16][8]:{...}` 报
   `Expected token of type "["`（官方先例 `init={token, ((), [42])}` 指路）。
3. **sel 可以作用于数组类型**（相位化写回靠它）—— XLS 按元素 lowering。
4. `array_update` 的 lowering 是**全数组写回**（每元素一个 mux）——size=8 无碍，
   size 上千时要另想形态。

### 实现要点（XlsBackend）

- `XlsProc.Builder` + `arrayIndex` / `arrayUpdate`（索引必须关键字形式 `indices=[x]`）。
- 每个 extern 一个数组 state（`reg_<inst>` / `cnt_<inst>: bits[W][N]`，init 全 0）；
  **extern 不参与相位 0 清零**（跨包持久，与 PHV 槽位本质不同）。
- 写回 = `array_update` 链 + 相位 sel（与 PHV 的 selNext 同构）：同拍多次写后写胜出。
- Counter.count = 读改写（`add(array_index(...), delta)` 再写回），与 Chisel 线
  的 CounterAdd 语义一致。
- `emitDagInto` 加 `ExternHooks`（read/write 回调，按语句相位构造、捕获谓词）；
  `actionDag` 支持 `MethodCall`（`lowering.lowerMethodCall` 本来就有 write/count）。

### 真·发现：XLS 会把「只写不读」的 state 当死代码优化掉

demo5 首跑：IR 里 `reg_per_proto`/`cnt_total` 和读改写链**全都在**，
但 codegen 出的 RTL 里寄存器**整个消失** —— counter 不进 PHV、无任何可观测下游，
XLS 的 DCE 删得完全合法（语义上输出确实与它无关）。

**修法：补观察通道 `ex_<inst>`**（对应 Chisel 线的 `io.ex_<name>`）：
- 走 `valid_data`（无背压）且**不带谓词** —— 观察口尽力而为，绝不反压主数据通路；
- 布局：元素 0 在最高位（与 PHV「先声明者在高位」同原则）；
- 数据取 `extNext`（本拍处理后的值）→ 观测者看到「已含本拍更新」的结果。

**教训：生成器里每一条 state 都必须有对外可观测路径，否则不是"没实现"而是
"会被下游工具静默删掉"** —— 而且 IR 层面完全看不出（要看到 codegen 之后才发现）。
