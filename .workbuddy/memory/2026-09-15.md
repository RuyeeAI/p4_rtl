# 2026-09-15

## p4c-XLS 方案 v2：范围裁剪调整

- 交付：更新 `docs/p4c-xls后端扩展方案.md`（v2，含 Key/Response 接口边界图）
- 用户决策的两项裁剪：
  1. **Match 只生成 Key/Response 接口，不生成存储本体** —— 表存储/匹配算法（EM/LPM/TCAM）全部外置。
  2. **本期不支持 PISA ALU 阵列** —— 不做 stage 内 ALU 资源预算、多表同 stage 打包、确定性流水划分。
- 裁剪带来的结构性变化：
  - 原"最大阻塞点"（XLS 无存储原语 → 需自研 TCAM/LPM RTL）**消失**，转为**接口契约定义**工作。
  - **新的头号风险 = 访存延迟的时序契约**。XLS `proc.next()` 是"每拍迭代一次"模型，外部存储器有 1–4 拍延迟。两条方案：纯握手（靠 flow control 吸收，但 XLS 是否保证此行为未文档化）/ 计数状态吸收固定延迟 L。**建议接口按握手定义、实现先走计数状态；M0 做最小闭环验证，不通则 M2 前提要重估。**
  - ALU 阵列移出后，M4 从"收敛"改为"基线评测"，工作量大幅下降。
  - `counter/meter/register` 可复用同一套外部资源接口基建，是裁剪顺带带来的红利。
  - `const_entries` 编译期内联为零成本优化，必须在生成器里做。
- 接口规范要点（已写入文档第 4 节）：每表一对通道、握手式为主 + 先按固定延迟 L 实现、串行（无 outstanding）、key 按 PIR 字段 MSB 对齐补零、mask 不由 XLS 侧输出（外部表项自带）、action_data 按"参数槽"布局、hit=0 走 XLS 内的 default_action。
- 工作量变化：MVP 7–11 → **5.5–8.5 人月**；到基线评测 15–22 → **8–12.5 人月**；M5（ALU 阵列 + 真实存储 IP）预留 +4–8 人月。
- 阶段重排：M0 接口打样(1.5–2.5) / M1 全流程无表(2–3) / M2 表接口接通(2–3) / M3 外部状态(1.5–2) / M4 基线评测(1–2)。
- 定位更新：这条路产出的是"**P4 逻辑 → RTL 生成器**"，不是"P4 → 完整可编程数据面"；存储、状态、调度全部外置。
- 新增文档小节：外部实现方可选形态（Python/C++ 行为模型 → EM-only RTL 模型 → 真实 TCAM/SRAM IP），验证链路不变——M2 起可直接喂 bmv2 同一份表项与状态做三级对拍。

## 复用资产审计：本地 P4C 与 p4x

- 交付：`docs/复用资产审计-本地P4C与p4x.md`（含模块级复用度清单）
- 审计对象：`Code-Repos/P4C`（自研 P4→Chisel 编译器）、`Code-Repos/p4x`（工具链封装）

### 重大发现（改变了 p4_rtl 的路线）

1. **P4C 的 XLS IR 文本输出已实测存在**：`P4C/build/demo{9,10,11}/ir/*.ir` 共 20+ 文件，内容为
   `package` / `fn(...) -> (...)` / `literal(value=N)` / `sub` / `array_index` / `tuple` / `ret name: (...)`
   —— 逐项对照 XLS IR 语法均合法。**这是整条路线成立的前提，需实测一次 XLS parser。**
2. **P4C 已完成 X8–X14 的 XLS 对齐**：`IrText`（.ir dump/parse/round-trip）、`Passes.balance`/`narrow`
   （对应 XLS 的 boolean unflattening / reassociation / narrowing）、`Scheduler.refine`（SDC-lite）、
   `Smt`+`Equivalence`（Z3 三级策略）、`IrStats`/`IrMinimizer`/BOM、`DelayModels.toJson`。
3. **唯一缺口 = Top 时序编排**：`IrText.dump(pkg, fnName, dag)` 只能 dump 单个 Dag → 单个 `fn`，
   无 proc/通道抽象（P4C 缺口清单已列入"后续"）。**但这件事在 Chisel 侧已做成**：
   `generated/p4c/Demo5Pipeline.scala` 里有 `_Ingress`（control）/ `_TopParser`（parser FSM）/ `_Top`（组装）。

### 代码规模与复用度

- P4C：main 5,381 行 / test 3,635 行（25+ 套件，185 tests 全绿）
- 可直接复用 ≈ **2,900 行（54%）**：Parser 710 / Ir 490 / IrText 346 / Smt 329 / IrBuilder 202 /
  Signature 199 / Lexer 159 / Directive 144 / Ast 109 / Tools 107 / Interp 96 / Repro 18
- 需改写 1,426 行：`ChiselBackend` → `XlsBackend`（编排逻辑照搬，目标从 Chisel Module 改成 XLS proc）
- XLS 路线下可暂缓 542 行：`SchedulePass` + `DelayModel`（XLS 自带调度器）
- 小改 504 行：`Cli` + `Generate`（加 `--xls` 输出）

### p4x 的价值

- `dist/bin/` 已有 **macOS/arm64 构建成功的完整工具链**：`p4c-bm2-ss`(19.8MB)、`p4test`(19.4MB)、
  `simple_switch`(4.5MB)、`simple_switch_CLI`、`psa_switch`、`pna_nic`、`p4chisel.jar`(6.6MB)、
  `share/p4c/p4include/`（v1model.p4 / core.p4 / psa.p4 等）→ **三级对拍第一级现成，不用重建**。
- `packaging/*.sh` 记录了 bmv2 在 macOS/arm64 的两处上游缺陷规避（`compat/bmv2_apple_portability.h`
  + dylib 链接行显式挂 xxhash/jsoncpp/gmp/pcap），以及 p4c 必须启用控制面（`ENABLE_BMV2` 依赖
  `ENABLE_CONTROL_PLANE`）等坑。
- 限制：`dist/` 依赖 Homebrew 6 个 dylib 绝对路径，换机/CI 需 `dylibbundler` 收口。
- p4x 非 git 仓库（775 行 Python，stdlib-only，子命令 sim/chisel/ppal/all）。

### 路线修正（已写入方案文档头部）

**"P4C(自研) → XLS IR 文本（已有）+ 新增 XlsBackend 生成 proc 编排 → XLS codegen → Verilog"**。
省掉 PIR 层、Python 生成器、DSLX 学习成本。

## p4_rtl 工程正式启动 + A0 门禁通过

**交付**：p4_rtl 从"文档目录"变为可运行工程；A0 门禁 ✅ 通过。

### 工程形态

- `p4_rtl` 建为**独立 sbt 工程**（git init 完成），fork 了 `../P4C/src/main/scala/P4C` 全部 17 个文件、5,381 行，
  **包名保持 `P4C`** 便于与上游 diff。上游基线 commit `8c7eaaf`（2026-09-11）。
- 新代码包名 `p4xls`，顶层 CLI `p4xls.Main`（子命令 `p4c` / `lint-ir` / `version`）。
- 关键前提已验证：**`src/main/scala/P4C` 全部源码无 chisel3 运行时依赖**，可打成轻量 fat jar。
- 工具链：sbt 1.12.6 + Scala 2.13.12 + JDK 26；本机**无 bazel / conda**，有 verilator/iverilog/cmake/ninja。
- `scripts/p4xls` 包装脚本用 `java -cp target/scala-2.13/classes:scala-library.jar` 直跑，绕过 sbt 启动开销（5s → 0.3s）。

### A0 门禁结论：25/25 通过

- 11 个 demo P4 → **25 个 `.ir`**，语法校验 **25/25 通过，0 issue**。
- **唯一不兼容点（已修）**：`array_index(arr, idx)` → 必须写 `array_index(arr, indices=[idx])`。
  - 根因：`ir_parser.cc:1065` `kArrayIndex` 用 `AddKeywordArg<vector<BValue>>("indices")` + `Run(arity=1)`；
    而 `ArgParser::Run`（`:329-376`）**位置参数与关键字参数分开解析**，`indices` 是 mandatory keyword
    → 位置写法同时触发 arity 不匹配 + 关键字缺失。
  - 修复：`IrText.scala:128`（生成）+ `:304`（解析，改用正则提取 `indices=[(\w+)]`）+ 文档注释。
- **已确认为兼容**（逐条对照源码）：`//` 注释（`ir_scanner.cc:156` `DropEndOfLineComment`）、
  `package` + 多 `fn`、`-> (T1, T2)` 元组返回、`ret name: (T,) = tuple(...)`、`sel(cond, cases=[])` 无 default、
  `zero_ext(x, new_bit_count=N)`、`bits[16][8]` 数组类型。
- P4C 实际用到 12 个 op：`add array_index bit_slice concat eq literal sel shll sub tuple xor zero_ext`。

### 新工具（可复用）

- `scripts/gen_op_contracts.py` → 从 `ir_parser.cc` **自动提取** op 参数契约（arity / 必选 / 可选关键字），
  产出 `config/op_contracts.json`（84 条：45 条显式 case + 39 条来自 `op_list.h` 的 default 分支）。
  坑：①模板参数含嵌套尖括号（`std::vector<BValue>`）需专门正则；②C++ case fallthrough
  （`case kZeroExt: case kSignExt:` 共享实现）需继承后继块；③`Run(ArgParser::kVariadic)` 非数字形式。
- `scripts/xls_ir_lint.py` → XLS IR 文本静态校验器。复现 scanner 词法 + 顶层结构 + 逐 op 契约校验。
  支持片段模式（`xls/ir/testdata/*.ir` 无 `package` 头，对应 `ParseFunction()` API 输入）。
- **可信度回归**：XLS 自带 768 个 `.ir` 做正样本 → 纯 `fn` 子集 **468/493 = 94.9%**；
  剩余失败均在 P4C 不生成的边缘语法（`token` 字面量、FFI 内嵌换行等）。

### 环境受阻

- `brew install bazelisk` 跑 21 分钟后失败：`Operation not permitted @ apply2files -
  /opt/homebrew/var/homebrew/locks/...` —— **Homebrew 内部文件操作被沙箱拒绝，非网络问题**。
  需在沙箱外执行。装好后可用 `bazel run //xls/tools:eval_ir_main -- <file.ir>` 把静态验证升级为真实 parser 验证。
- 顺手坑：Scala 注释**可嵌套**，文档注释里写 `out/ir/*.ir` 会因 `/*` 开启嵌套导致 `unclosed comment`。
