# 2026-09-15

## p4c-XLS 方案 v2：范围裁剪调整

- 交付：更新 `docs/p4c-xls后端扩展方案.md`（v2，含 Key/Response 接口边界图）
- 用户决策的两项裁剪：
  1. **Match 只生成 Key/Response 接口，不生成存储本体** —— 表存储/匹配算法（EM/LPM/TCAM）全部外置。
  2. **本期不支持 PISA ALU 阵列** —— 不做 stage 内 ALU 资源预算、多表同 stage 打包、确定性流水划分。
- 裁剪带来的结构性变化：
  - 原"最大阻塞点"（XLS 无存储原语 → 需自研 TCAM/LPM RTL）**消失**，转为**接口契约定义**工作。
  - **新的头号风险 = 访存延迟的时序契约**。XLS `proc.next()` 是"每拍迭代一次"模型，外部存储器有 1–4 拍延迟。两条方案：纯握手（靠 flow control 吸收，但 XLS 是否保证此行为未文档化）/ 计数状态吸收固定延迟 L。**建议接口按握手定义、实现先走计数状态；M0 做最小闭环验证，不通则 M2 前提要重估。**
  - ALU 阵列移出后，M4 从"收敛"改为"基线评测"，工作量大幅下降。
  - `counter/meter/register` 可复用同一套外部资源接口基建，是裁剪顺带带来的红利。
  - `const_entries` 编译期内联为零成本优化，必须在生成器里做。
- 接口规范要点（已写入文档第 4 节）：每表一对通道、握手式为主 + 先按固定延迟 L 实现、串行（无 outstanding）、key 按 PIR 字段 MSB 对齐补零、mask 不由 XLS 侧输出（外部表项自带）、action_data 按"参数槽"布局、hit=0 走 XLS 内的 default_action。
- 工作量变化：MVP 7–11 → **5.5–8.5 人月**；到基线评测 15–22 → **8–12.5 人月**；M5（ALU 阵列 + 真实存储 IP）预留 +4–8 人月。
- 阶段重排：M0 接口打样(1.5–2.5) / M1 全流程无表(2–3) / M2 表接口接通(2–3) / M3 外部状态(1.5–2) / M4 基线评测(1–2)。
- 定位更新：这条路产出的是"**P4 逻辑 → RTL 生成器**"，不是"P4 → 完整可编程数据面"；存储、状态、调度全部外置。
- 新增文档小节：外部实现方可选形态（Python/C++ 行为模型 → EM-only RTL 模型 → 真实 TCAM/SRAM IP），验证链路不变——M2 起可直接喂 bmv2 同一份表项与状态做三级对拍。

## A1：XLS 环境搭建（macOS/arm64 自建）

**交付**：`scripts/{env.sh,bootstrap_xls_env.sh,patch_xls_module.sh,setup_xls_harness.sh,xls_ir_verify.sh}`
+ `config/{xls_MODULE.bazel.minimal,xls_ROOT_BUILD.minimal,bazel_downloader.cfg}`
+ `xls_harness/{ir_check_main.cc,BUILD.bazel}`；报告 `docs/A1-环境报告.md`。

### 排除的路：没有任何现成 macOS 产物

- GitHub Release 只有 `xls-*-linux-x64.tar.gz`；conda `litex-hub` 234 个文件**全是 linux-64**；
  conda-forge 无；PyPI 的 `xls` 是 JS-XLS 的移植（无关）。
- 本机**无 docker / colima / podman / lima / nerdctl**，也无 `qemu-x86_64` → 跑不了 linux 产物。
- **结论：只能源码自建。**

### 三个网络/平台硬约束

1. **GitHub 直连不可用**（`HTTP 000`），但 `gh-proxy.com` / `ghproxy.net` / `ghfast.top` 均 200
   （40–75 KB/s）；`bcr.bazel.build` 200 可用。→ bazelisk 用 `BAZELISK_BASE_URL` 走镜像；
   Bazel 用 `--downloader_config` 的 `rewrite` 把 `github.com/*` 改写到三个镜像（互备）。
2. **本机有 WorkBuddy 透明代理**（`HTTP_PROXY=http://127.0.0.1:64321`），Bazel 走 CONNECT 隧道
   访问 GitHub 必失败：`Unable to tunnel through proxy. Proxy returns "HTTP/1.1 502 Bad Gateway"`。
   → `scripts/env.sh` 的 `p4xls_bazel()` 包装**显式清空 `HTTP(S)_PROXY`/`ALL_PROXY`**。
3. **bazelisk 默认按 "latest" 查 GCS**（`www.googleapis.com` 不可达，HTTP 000）→ 必须
   `export USE_BAZEL_VERSION=$(cat third_party/xls/.bazelversion)` = **8.7.0**，绕过 GCS。

### 核心坑 1：Bzlmod 全图解析会强制 clone OpenROAD/LLVM/PDK

XLS 原版 `MODULE.bazel` 面向全功能，Bzlmod **只要 module 在依赖图里就要拉源码读它的 BUILD**，
于是哪怕只编译 `//xls/ir:ir_parser` 也要下：OpenROAD（`init_submodules=True`，GB 级）、
LLVM 源码、**12 个 SkyWater/ASAP7 PDK**、Yosys/Icarus、Perfetto、Verible、qt-bazel、Maven。
**实测 6 分钟只拉到 8.6MB 就卡在 OpenROAD**（直连 clone ~30KB/s）。

依据：`xls/ir/BUILD`、`xls/common/BUILD`、`xls/codegen/BUILD` 中
`org_theopenroadproject`/`rules_hdl`/`llvm-project`/`perfetto`/`verible` **出现次数均为 0**。

→ `config/xls_MODULE.bazel.minimal` 摘掉 15 个依赖（45→30）。
两个易错点：① `googletest`/`google_benchmark` 要保留（`xls/*/BUILD` 有 label 引用），
但去掉 `dev_dependency`；② `zlib-ng`/`zstd` 必须保留 `repo_name = "llvm_zlib"/"llvm_zstd"`，
否则与 `use_repo(zstd_ext,"zstd")` 撞名报错。

### 核心坑 2：`.bazelrc` 的 Starlark flag 悬空（最坑）

摘掉 LLVM 后，`third_party/xls/.bazelrc:83` 这行变成悬空引用：

```
build --@llvm-project//third-party:llvm_enable_zstd=false
```

`--@repo//pkg:flag` 是 Bazel 的 **Starlark 命令行 flag** 语法，Bazel 在**装配命令行阶段**
就要解析该 repo，报：

```
ERROR: @llvm-project//third-party:llvm_enable_zstd :: Error loading option
@llvm-project//third-party:llvm_enable_zstd: No repository visible as
'@llvm-project' from main repository.
```

**关键特征**：与"构建哪个 target"**完全无关** —— 零 XLS 依赖的空 `cc_binary` 也照报。
本轮在这上面误判了三次（先怀疑 `xls/common/file/BUILD`，再怀疑 BCR 的 `zstd` module，再怀疑存根）。

**可复用的定位法**：把 `MODULE.bazel` 砍到只剩 `module()` + `bazel_dep(rules_cc)` 再构建。
**若极简依赖图仍报同一个错 → 问题不在依赖图，而在命令行/配置文件层面** →
然后 `grep -nE '\-\-@' .bazelrc` 一击命中。

### 核心坑 3：根 BUILD 被隐式加载

`xls/common/BUILD` 的 `cc_library` 通过 Bazel 的
`package(default_applicable_licenses = ["//:license"])` 机制**隐式依赖 `//:license`**，
而该 target 定义在根 BUILD → **根包必然被加载** → 原版根 BUILD 里
`load("@hedron_compile_commands//:refresh_compile_commands.bzl", ...)` 与
`tools = ["@com_google_fuzztest//bazel:setup_configs"]` 双双报缺。

→ `config/xls_ROOT_BUILD.minimal` 只保留 `//:license` + `exports_files` +
`default_visibility`，去掉 hedron/fuzztest 引用。

### 补丁机制

`scripts/patch_xls_module.sh apply|restore|status|diff`，处理三个文件
（`MODULE.bazel` / `.bazelrc` / 根 `BUILD`），原文件备份为 `*.orig` 可一键还原。
bazelisk/bazel/输出目录全部隔离在工程内 `.tools/`，不污染 `~/.cache`。

### 一次失败的诊断记录（值得记住）

`sed -i ''` 在 `find -exec` 中空参数丢失 → 改用 Python 做批量替换。
`pgrep -f "bazel"` 会匹配到自身命令行（含 "bazel" 字样）→ **把自己杀了**，避免用这个模式清理进程。
macOS 的 `xargs` **不支持 `-a`**，要用 `xargs cmd < file`。
传文件列表给子命令时别写成 `"$(cat list.txt)"` —— 双引号会把整串当成**单个**参数，
要用 `xargs` 或裸展开。

### 补丁三：`@rules_hdl` 存根

前两个补丁之后还剩一处：`xls/build_rules/*.bzl` 三处引用 `@rules_hdl`
（`xls_rules.bzl:20`、`xls_codegen_fdo_rules.bzl:20` 要 `StandardCellInfo`；
`xls_macros.bzl:22-23` 要 `synthesize_rtl`/`verilog_library`）。
而 `xls/codegen/BUILD` 会 load `xls_build_defs.bzl` → 串到 fdo rules，
只要构建任何依赖 `//xls/codegen` 的目标（`//xls/ir:ir_parser` 依赖 `//xls/codegen:module_signature`）就炸。

**真 rules_hdl 不能加回**：其 MODULE.bazel 依赖 openroad（git_override + init_submodules，GB 级）、
verilator、abc、tcl_lang、rules_7zip、readline、libffi、bzip2、gperf；
且它给 openroad 写的 git_override **在非 root module 下不生效** → 版本解析直接失败。

→ 用 `xls_harness/rules_hdl_stub/` 提供最小 repo（`pdk`/`synthesis`/`verilog` 三个包，
导出 `StandardCellInfo` provider 与几个空 rule），
在 MODULE 里用 `bazel_dep(name="rules_hdl", version="0.0.0")` +
`local_path_override(module_name="rules_hdl", path="p4xls_harness/rules_hdl_stub")` 挂载。
