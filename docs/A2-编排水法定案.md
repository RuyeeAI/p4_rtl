# A2 编排水法定案（P0）

> 日期：2026-09-16
> 上游依赖：`docs/M0-接口打样报告.md`（M0 发现「token 链 + 阻塞通道」的 proc 拿不到 II=1）
> 结论：**采用方案 (c) —— 并行 token 拓扑，通道操作不串链。**

---

## 0. 结论

| 项 | 结果 |
|---|---|
| **定案** | **通道操作不串在同一 token 链上**；用 `after_all` 在末尾汇聚 |
| 最小 II | 串行链 **2** → 并行拓扑 **1**（stages 1..4 全部可行） |
| 功能 | ✅ 全部通过（含新增的背压 case），**行为不变** |
| 附加收益 | RTL 寄存器 9 → 4 个；RTL 规模 3812 → 2474 字节（**−35%**）；端到端延迟反而少 1 拍 |
| II 的表达方式 | 写进 IR：`#[initiation_interval(1)]`（自描述，不依赖 driver 参数） |

---

## 1. 问题

M0 打样发现：`state_read(tok) → send → receive → send → next_value(tok)` 这条
**循环携带依赖**路径让调度器判定 II=1 不可达（stage 数 1/2/3/4 全部失败）。

根因在 `xls/scheduling/run_pipeline_schedule.cc:232-242`：

```cpp
  for (Next* next : proc->next_values()) {
    for (StateRead* state_read : proc->GetStateReadsByStateElement(next->state_element())) {
      const int64_t backedge_length = schedule_cycle_map[next] - schedule_cycle_map[state_read];
      pessimistic_worst_case_throughput = std::max(..., backedge_length + 1);
    }
  }
```

→ **可达的最小 WCT = 每个 state 元素「next_value 与 state_read 的 cycle 距离 + 1」的最大值。**
II=1 要求每个 state 的读与写落在**同一 cycle**。

但这里有两个可能的瓶颈来源，**必须区分开**：

- **H1**：通道操作（`send`/`receive`）本身就无法与其 state 读写照排到同一拍；
- **H2**：只是 token **串链**把多个通道操作串成了一条长回边。

**H1 成立 → 无解**（任何含通道的 proc 都只能 II≥2）；
**H2 成立 → 只需改 token 拓扑**。

---

## 2. 实验设计

四个变体，只改 token 拓扑，其余（FSM、通道、predicate）保持一致：

| 变体 | 结构 | 看什么 |
|---|---|---|
| **B1** | 只有 `send`（`ii_probe_send.ir`） | 单个通道操作在回边上时能否 II=1 |
| **B2** | 只有 `receive`（`ii_probe_recv.ir`） | 同上，且 receive 是阻塞的 |
| **B3** | **并行 token**：三个通道操作都直连 `state_read(tok)`，末尾 `after_all` 汇聚（`ii_probe_parallel_tok.ir`） | H2 是否成立 |
| **B4** | 基线：串行 token 链（`m0_key_rsp_loop_serial_token.ir`） | 对照（已知 II=2） |

**测量协议**（`scripts/ii_sweep.sh`）：对 stages ∈ 1..4、wct ∈ 1..3 逐个尝试，
**最小的能成功的 wct 就是该结构的最小可行 II**。
依据上游语义（`run_pipeline_schedule.cc:456-463`）：
不设 wct = 必须为 1；**0 = 不约束**；N = 必须恰好为 N。

### 推导

- **B1、B2 都是 II=1** → **H1 被否定**：通道操作（含阻塞 `receive`）本身
  完全可以与其 state 读写照排到同一拍。
- **B3 是 II=1 而 B4 是 II=2**，两者只差 token 拓扑 → **H2 成立**：
  瓶颈就是 token **串链**形成的长回边。
- **B4 在 stages=1 时完全不可调度**（连 wct=3 都失败）—— 因为那条回边跨了 4 个操作，
  一级流水装不下。这也解释了 M0 当时为什么在 stages 数上怎么调都不行。

## 4. 定案与落地

### 4.1 拓扑改动（唯一改动）

```text
串行（旧，II=2）：
  state_read(tok) → send(key) → receive(rsp) → send(result) → next_value(tok)

并行（新，II=1）：
  s_key = send(tok__1, ...)        ┐
  recv  = receive(tok__1, ...)     ├─ 三个都直接接 state_read(tok)，互不串链
  s_out = send(tok__1, ...)        ┘
  next_value(tok) = after_all(s_key, tok__2, s_out)   ← 只在末尾汇聚
```

### 4.2 语义等价性的依据（**这是前提条件，不是可选项**）

三个通道操作的 predicate `is_idle` / `is_wait` / `is_disp` 由 FSM 相位派生，
**互斥**（一个 2-bit phase 只能取一个值），不会同拍为真。

正因为互斥：
- 去掉串行 token 依赖**不影响功能**（不会有两个操作争同一拍的顺序）；
- 每个相位实际上只有一个通道操作会真正执行。

> ⚠️ **若 predicate 不保证互斥，不能这样拆链** —— 见 §5.2。

### 4.3 功能复验（testbench 未改，模块名/端口不变）

```
---- case 1: 计划等待 2 拍后才给 rsp ----
  [ok] key 在第 0 拍发出
  [ok] result 在第 3 拍出现，数据 = deadbeef（与 rsp 一致）

---- case 2: 计划等待 7 拍后才给 rsp ----
  [ok] key 在第 0 拍发出
  [ok] result 在第 8 拍出现，数据 = 12345678（与 rsp 一致）

---- case 3: 背压测试（两个 rdy 先拉 0 再放开）----
  [ok] 背压下 key 与 result 均未丢失，数据正确 = cafe0001

 结果：全部通过 —— 时序契约成立
```

对比旧版（II=2）：

| | 等 2 拍 → result | 等 7 拍 → result | 额外延迟 |
|---|---|---|---|
| 旧（II=2） | 第 4 拍 | 第 9 拍 | 2 拍 |
| **新（II=1）** | **第 3 拍** | **第 8 拍** | **1 拍** |

**吞吐翻倍，延迟还少一拍。**

### 4.4 RTL 结构对比

| | 旧（II=2） | 新（II=1） |
|---|---|---|
| 寄存器 | 9 个（含 `__tok_full`、两个 `*_already_done_reg`） | **4 个** |
| state 更新条件 | `p0_stage_done = __tok_full & stage_outputs_ready_0 & active_outputs_ready_0` | `stage_outputs_ready_0` |
| 输出就绪检查 | 显式 `active_outputs_ready_0` | 折进 `active_outputs_ready_1` |
| RTL 字节 | 3812 | **2474（−35%）** |

新版关键行（`out/m0/m0_key_rsp_loop.v`）：

```verilog
assign active_inputs_valid_1 = rsp_in_vld | ~is_wait;              // 等 response 的机制没变
assign active_outputs_ready_1 = (key_out_rdy | ~is_idle) & (result_out_rdy | ~is_disp);
assign stage_outputs_ready_0 = ~p1_inputs_valid | p1_stage_done;   // 背压没变
assign rsp = is_wait ? rsp_in : 32'h0000_0000;                     // WAIT 拍锁存
assign result_out = __rsp_hold;
```

**M0 的两条核心机制（等 response、背压）在改动后完全保留**，
case 3 专门验证了背压下 key / result 不丢。

### 4.5 II 的表达方式：写进 IR

`#[initiation_interval(1)]` 属性在 `:passes` 修复后**已可用**（实测：带属性 + 不设 wct
生成 2474 字节，与 `--wct=1` 完全一致）。

**定案：II 写进 IR，不用 driver 参数。** 理由：生成的 `.ir` 自描述，
任何 XLS 工具都能正确处理，不依赖我们 driver 的调用约定。

> 注意：若同时给了 `--wct=N`，**命令行选项优先**于属性
> （`run_pipeline_schedule.cc:464-520`）。

## 5. 对 A2 生成器的硬性要求

### 5.1 通道操作不得串链

同一 proc 内的多个通道操作**不要**串成一条 token 链；应从同一个
`state_read(tok)` 出发，末尾用 `after_all` 汇聚。
（否则 II=2，且 stages=1 时完全不可调度。）

### 5.2 **前提条件必须校验：同 proc 内通道操作的 predicate 互斥**

拆链的正确性**完全依赖** predicate 互斥。

生成器必须做到其一：

- **静态可证**（推荐）：若各通道操作的 predicate 由同一个状态变量的
  互斥取值派生（如本文的 FSM 相位），记录该证明并拆链；
- **无法证明时**：退化为串行 token 链（接受 II=2），并**显式报出诊断**
  —— 不要静默拆链，否则行为不确定。

> 这条是 A2 最容易出事的地方：静默拆链会产出一个"能编译、能过仿真、
> 但在真实硬件上行为不确定"的 RTL。

### 5.3 其余已知硬性规则（M0 积累）

| # | 规则 | 来源 |
|---|---|---|
| 1 | proc-scoped `chan_interface` 的 `strictness` **必填** | `verifier.cc:384` |
| 2 | 节点名 `<op>.<N>` 的后缀 N **必须等于** `id=` | 解析器报错 |
| 3 | **引用必须先于定义** | 解析器报错 |
| 4 | II 用 `#[initiation_interval(N)]` 写进 IR | 本定案 §4.5 |

### 5.4 stages 与 II 正交

II=1 与流水级数是**两个独立维度**：本实验里 stages=1..4 都能做到 II=1。
stages 应由延迟模型推导。当前用 PDK 存根（D2 决策）→ 建议默认 **stages=2**，
M4 引入真工艺库后再校准。

## 6. 边界与遗留

| # | 事项 | 说明 |
|---|---|---|
| 1 | **未验证：多通道 / 多表在同一 proc 内的 II** | A3 一定会遇到。**建议 A3 的第一个检查点就扫一遍 II**（`scripts/ii_sweep.sh` 现成） |
| 2 | 未验证：`#[initiation_interval]` 在多 proc 包 / proc 实例化下的行为 | 若 A2 采用多 proc 拆分，需复核 |
| 3 | 候选 (a) 拆分 proc 未做实验 | **现已无必要**（(c) 已解决）；若将来 (c) 不适用（predicate 无法证明互斥）再回头做 |
| 4 | 真实面积/时序未评估 | 需真 PDK（D2 决策：M4 前再评估） |
| 5 | stages 最优值未扫 | 与延迟模型相关，等真 PDK |

### 结论：候选方案取舍

| 候选 | 结论 |
|---|---|
| **(a) 拆分 proc** | ❌ 不需要（成本高、接口多一层） |
| **(b) 接受 II=2** | ⚠️ 降级为**兜底**：当 predicate 无法证明互斥时使用 |
| **(c) 并行 token** | ✅ **定案** |
