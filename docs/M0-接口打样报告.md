仿真输出：

```
---- case 1: 计划等待 2 拍后才给 rsp ----
  → 第 2 拍给出 rsp_in_vld=1, data=deadbeef (rsp_in_rdy=1)
  [ok] key 在第 -1 拍发出
  [ok] result 在第 4 拍出现，数据 = deadbeef（与 rsp 一致）

---- case 2: 计划等待 7 拍后才给 rsp ----
  → 第 7 拍给出 rsp_in_vld=1, data=12345678 (rsp_in_rdy=1)
  [ok] key 在第 -1 拍发出
  [ok] result 在第 9 拍出现，数据 = 12345678（与 rsp 一致）
```

**最关键的一条**：等待 2 拍 → 结果在第 4 拍；等待 7 拍 → 结果在第 9 拍。
两个 case 的差值是**恒定的 2 拍**（流水深度），而总延迟随 rsp 到达时刻线性变化
—— 这正是「等到 response 真的回来」（郝宇定义的 L = 最大延时值），**而不是死等固定拍数**。

## 1. M0 要验的问题

XLS 的 `proc` 是「每拍迭代一次」的模型，外部存储器有固定/可变延迟。
方案里把「**访存延迟的时序契约**」列为头号风险，并注明：

> XLS 是否保证 proc 内这种"发出后插等待"的行为，**文档里没有承诺**。

郝宇对语义的澄清：

> **L 是查找的最大延时值，response 返回时后续逻辑才开始工作。**
> 所以不是"死等固定 L 拍"，而是"等到 response 真的回来"。

### 2.1 M0 的 proc 结构

```
IDLE ──(send key)──→ WAIT ──(receive rsp，阻塞)──→ DISPATCH ──(send result)──→ IDLE
```

| 通道 | 方向 | 作用 |
|---|---|---|
| `key_out` | send | 发给外部存储器的查找键（64b） |
| `rsp_in` | receive | 外部存储器返回的 response（32b） |
| `result_out` | send | **拿到 response 后才启动**的后续逻辑输出（32b） |

核心机制：`receive(predicate=is_wait, channel=rsp_in)`
—— WAIT 相位且数据未就绪时，整个 proc 迭代被 stall，`next_value` 一并推迟。

### 2.2 生成的 RTL 如何实现"等"

`out/m0/m0_key_rsp_loop.v` 的关键 4 行（原样摘录）：

```verilog
assign rsp_in_rdy            = p1_stage_done & p0_is_wait;
assign active_inputs_valid_1 = rsp_in_vld | ~p0_is_wait;
assign stage_outputs_ready_0 = ~p1_inputs_valid | p1_stage_done;
assign p0_stage_done         = __tok_full & stage_outputs_ready_0 & active_outputs_ready_0;
assign rsp                   = p0_is_wait ? rsp_in : 32'h0000_0000;
assign result_out            = __rsp_hold;
```

读法：

- `active_inputs_valid_1`：**在 WAIT 相位，stage1 的 valid 完全由 `rsp_in_vld` 提供**。
  数据没来 → valid=0 → `p1_stage_done=0`。
- `stage_outputs_ready_0 = ~p1_inputs_valid | p1_stage_done`：stage1 没完成时
  stage0 不许推进（**背压**）。
- 两者叠加 → `p0_stage_done=0` → **整拍 stall，state 寄存器不更新**（`__phase` 保持）。
- `rsp = p0_is_wait ? rsp_in : 0` 与 `next_rsp_hold`：response 只在 WAIT 拍被锁存，
  DISPATCH 拍输出 `__rsp_hold`。

**这 4 行就是"等到 response 返回才继续"的硬件实现，与我们的推理完全一致。**

### 2.3 testbench 的验收判据

1. `key_out` 发出一次 key，数据 = `0xa5a5a5a5a5a5a5a5`
2. **`rsp_in_vld` 从未拉高之前，`result_out_vld` 必须一直为 0**
3. 给出 `rsp_in_vld` + 数据后，`result_out` 出现**同一数据**
4. 换一个不同的等待拍数重跑，行为一致（排除"死等固定 L 拍"）
5. **背压不丢数据**：`key_out_rdy` / `result_out_rdy` 为 0 期间不得发生传输，
   放开后数据完好（case 3，P0 期间补充）

## 3. 打样过程中必须记住的 6 个坑

> 这些都是**踩过并已解决**的，A2 生成器与后续调试会反复遇到。

### K1 ——「放宽 II」是必要条件，`--wct=2` 是解法

`xls/scheduling/run_pipeline_schedule.cc:232-242`：

```cpp
  for (Next* next : proc->next_values()) {
    for (StateRead* state_read : proc->GetStateReadsByStateElement(next->state_element())) {
      const int64_t backedge_length = schedule_cycle_map[next] - schedule_cycle_map[state_read];
      pessimistic_worst_case_throughput = std::max(pessimistic_worst_case_throughput, backedge_length + 1);
    }
  }
```

→ **可达的最小 WCT = 每个 state 元素「next_value 与 state_read 的 cycle 距离 + 1」的最大值。**
II=1 要求每个 state 的读与写落在**同一 cycle**。

我们的 proc 里 token 的状态回边是 `state_read(tok) → send → receive → send → next_value(tok)`，
跨多拍 → **II=1 不可达**。实测 stage 数 1/2/3/4 全部报：

```
cannot achieve full throughput. Try `--worst_case_throughput=2`
```

**`--wct=2` 后调度通过，Verilog 正常生成。**

> **✅ 已解决（P0，2026-09-16）**：瓶颈**不是**通道操作本身，而是 token **串链**。
> 把三个通道操作改成都直连 `state_read(tok)`、末尾 `after_all` 汇聚后，
> **最小 II = 1**（stages 1..4 全部可行），功能不变。
> 详见 [`docs/A2-编排水法定案.md`](A2-编排水法定案.md)。

### K2 —— `worst_case_throughput` 的语义反直觉

`run_pipeline_schedule.cc:456-463` 原注释：

> a value of **0** means the scheduler is free to choose any WCT it wants
> and **nullopt means the value must be exactly 1**.

| 取值 | 含义 |
|---|---|
| 不设置 | **必须 II=1** |
| `0` | **不约束**（让调度器自选） |
| `N>0` | **必须 = N** |

### K3 —— 漏 `//xls/codegen_v_1_5:passes` 会报一个极具误导性的错

**这是本轮最大的坑。** 症状：

```
❌ codegen 失败: default_pipeline is not registered.
   Have [opt_pass<arith_simp>, ..., opt_pass<default_pipeline>, ...]
```

**误导点一**：报错列表里**明明有** `opt_pass<default_pipeline>`，让人以为注册表没问题。
实际上 `GetCodegenPassRegistry()` 是**独立于优化 pass 注册表**的另一张表，
`default_pipeline` 这个 compound pass 由 `xls_default_codegen_pass_registry(name="passes")` 提供。

**误导点二（更坑）**：**这个错误只在"调度成功之后"才会出现。**
调度失败时会先报 `cannot achieve full throughput`，于是很容易把它误判成调度问题，
去反复调 `--stages` / `--wct` —— 我在这里绕了很久。

**正解**：`//xls/tools:codegen`（官方）在 `xls/tools/BUILD:845` 显式依赖
`//xls/codegen_v_1_5:passes`，而我们自建 driver 只链了 `//xls/codegen_v_1_5:codegen`
（它的 deps 里**没有** `:passes`）。补上即解。

> 教训：**自建 driver 时必须把「官方 main 的 deps」逐个对照一遍**，
> 尤其是这类"注册表/插件"式的 alwayslink 依赖 —— 它们不体现在 API 上。

顺带记：这个错误用**官方自带的最小 proc 样本**
（`xls/ir/testdata/ir_parser_round_trip_test_ParseIIProc.ir`）也能复现，
这是判定"是工具链问题还是我的 IR 问题"的最快捷对照法。

### K4 —— `clock_name` 是必填项

`xls/codegen_v_1_5/scheduled_block_conversion_pass.cc:56-61`：

```cpp
  if (!options.clock_name().has_value()) {
    return absl::InvalidArgumentError(
        "Clock name must be specified when generating a pipelined block");
  }
```

官方 `codegen_main` 不报，是因为它的 flag handler registry 会填默认值。
自建 driver 必须显式 `cg.clock_name("clk")`，并建议同时
`cg.reset("rst", /*asynchronous=*/false, /*active_low=*/false, /*reset_data_path=*/true)`。

### K5 —— proc-scoped `chan_interface` 的 `strictness` 是必填项

```
verifier.cc:384 channel_interface->strictness().has_value()
ChannelInterface `key_out` in proc `key_rsp_loop` is streaming but has no strictness value
```

**两种写法默认值不同**：老式顶层 `chan` 声明不写时默认
`proven_mutually_exclusive`（`ir_parser.cc:2964`），而 **proc-scoped 的 `chan_interface`
走 `SetStrictness(optional)`，缺省即 `nullopt` → 校验不过**。

### K6 —— IR 文本的两条硬性规则

1. 节点名形如 `<op>.<N>` 时，**后缀 N 必须等于 `id=` 属性值**
   （报错：`The id '1' in node name literal.1 does not match the id '2' specified as an attribute`）
2. **引用必须先于定义**（报错：`Referred to a name ... that was not previously defined`）

## 4. 一个对 A2 接口设计有直接影响的观察

**XLS 生成的 `rsp_in_rdy` 语义是「本拍完成一次接收」，而不是「我随时能收」。**

```verilog
assign rsp_in_rdy = p1_stage_done & p0_is_wait;
```

没有数据时（WAIT 相位 + `rsp_in_vld=0`）→ `p1_stage_done=0` → **`rsp_in_rdy` 也是 0**。

这仍然是合法的 valid/ready 协议（`vld & rdy` 同拍表示一次传输），
但**外部存储器 / 表接口的 RTL 不能把 `rdy` 当作"可以发数据"的许可信号来用**。
契约里必须写清楚：**由 XLS 侧决定何时接收，外部只负责在数据就绪时拉 `vld` 并保持**。

> 这条要写进 A3 的 Key/Response 接口规范，否则外部行为模型很容易写错。

## 5. 对 A2 / M2 的影响与建议

### 5.1 II 的吞吐含义（✅ 已定案）

原始配置（`--stages=2 --wct=2`）的 II=2 意味着**每 2 拍才能启动一次新迭代**，
对 PISA「一拍一包」是硬约束。

**P0 已定案：采用并行 token 拓扑，最小 II = 1。** 三个候选的最终取舍：

| 方案 | 结论 |
|---|---|
| (a) 拆分 proc | ❌ 不需要（成本高、接口多一层） |
| (b) 接受 II=2 | ⚠️ 降级为**兜底**：当通道操作的 predicate 无法证明互斥时使用 |
| **(c) 并行 token** | ✅ **定案** —— II=1，功能不变，RTL 规模 −35% |

详见 [`docs/A2-编排水法定案.md`](A2-编排水法定案.md)。

### 5.2 对接口规范的影响

- `rsp_in_rdy` 语义（§4）必须写进规范
- Key/Response 的握手机制已被验证可用，**不需要写死 L**
- 建议 M2 的外接存储器先用**行为模型**（Verilog），延迟可参数化

### 重要操作纪律（本轮踩过，代价 22 分钟）

- **不要 kill 正在跑的 Bazel 构建。** 被 SIGTERM 的客户端会在 server 侧留下**悬挂命令锁**
  （现象：`Another command (pid=...) is running. Waiting for it to complete`，而该 pid 已不存在）。
- 此时 `kill -9` server 会让在飞动作作废 → **触发全量重编**（实测 22 分钟）。
- 增量构建正常是 **10 秒 ~ 4 分钟**；首次全量 **25 分钟**。
