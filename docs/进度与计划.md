### M0 接口打样 ✅（2026-09-16）—— 本项目最关键的一次验证

**问题**：XLS 的 `proc` 是「每拍迭代一次」模型，外部存储器有固定/可变延迟。
「发出后插等待」这个行为**上游文档没有承诺**，是方案里的头号风险。

**郝宇澄清的语义**：L 是查找的最大延时值，**response 返回时后续逻辑才开始工作**
→ 不是"死等 L 拍"，而是"等到 response 真的回来"。

**结论：✅ 契约成立。**

```
case 1: 等 2 拍后给 rsp → result 第 4 拍出现，data=deadbeef  ✓
case 2: 等 7 拍后给 rsp → result 第 9 拍出现，data=12345678  ✓
```

**最强的一条证据**：两个 case 的延迟差**恒定**（当前为 5 拍差值对应 2 拍流水深度），
总延迟随 rsp 到达时刻线性变化 → 这是「等到 response 真的回来」，**不是死等固定拍数**。
且等待期内 `result_out_vld` 全程为 0（"后续逻辑必须等"的直接证据）。

**生成的 RTL 实现"等"的关键行**（`out/m0/m0_key_rsp_loop.v`，当前版本）：

```verilog
assign active_inputs_valid_1 = rsp_in_vld | ~is_wait;            // WAIT 时 valid 必须来自 rsp_in_vld
assign stage_outputs_valid_1 = p1_inputs_valid & active_inputs_valid_1;
assign stage_outputs_ready_0 = ~p1_inputs_valid | p1_stage_done; // 背压：stage1 没完成 stage0 不推进
assign p1_stage_done = stage_outputs_valid_1 & active_outputs_ready_1;
// → 三者叠加即整拍 stall，state 全部不更新。注意**没有出现任何 rdy 信号**。
```

**六个必须记住的坑**（A2 生成器与后续调试会反复遇到，详见报告 §3）：

| # | 坑 | 要点 |
|---|---|---|
| **K3** | **漏 `//xls/codegen_v_1_5:passes`** | 报 `default_pipeline is not registered`。**两个误导点**：① 报错列表里"明明有"该项（codegen 与优化的 pass 注册表是两张表）② **该错误只在调度成功之后才出现**，极易误判为调度问题。官方 `xls/tools/BUILD:845` 有显式依赖，`:codegen` 没有 |
| **K1** | **`token 链 + 阻塞通道` 的 proc 拿不到 II=1** | 依据 `run_pipeline_schedule.cc:232-242`。stage 1/2/3/4 全部失败；`--wct=2` 后通过 → **对 PISA「一拍一包」是硬约束，A2 必须先决策** |
| **K2** | `worst_case_throughput` 语义反直觉 | **0 = 不约束**；**不设 = 必须为 1**；N = 必须为 N（`run_pipeline_schedule.cc:456-463`） |
| **K4** | `clock_name` 必填 | `scheduled_block_conversion_pass.cc:56-61`；官方 main 靠 flag registry 填默认值 |
| **K5** | proc-scoped `chan_interface` 的 `strictness` 必填 | 老式顶层 `chan` 有默认值，proc-scoped 走 `SetStrictness(optional)` 没有 |
| **K6** | IR 文本两条硬规则 | ① 节点名 `<op>.<N>` 的后缀必须等于 `id=` ② 引用必须先于定义 |

**一个判定技巧**（省了大量排查时间）：拿官方最小 proc 样本
`xls/ir/testdata/ir_parser_round_trip_test_ParseIIProc.ir` 跑同一个 driver，
**能复现说明是工具链问题、不是自己的 IR 问题**。

### P0 —— II 编排水法定案 ✅（2026-09-16）

**问题**：M0 发现「token 链 + 阻塞通道」的 proc **拿不到 II=1**（每 2 拍才能启动一次迭代），
而 PISA 要求「一拍一包」—— 这是硬约束，必须先定案否则 A2 生成器要返工。

**实验设计**：四个变体只改 token 拓扑，其余（FSM / 通道 / predicate）保持一致，
用 `scripts/ii_sweep.sh`（stages × wct 矩阵扫描）测**最小可行 II**。

| 变体 | 结构 | 最小 II |
|---|---|---|
| B1 | 只有 `send` | **1** |
| B2 | 只有 `receive` | **1** |
| **B3** | **并行 token**（通道操作都直连 `state_read(tok)`，末尾 `after_all` 汇聚） | **1** |
| B4 | 基线：串行 token 链 | 2（且 stages=1 完全不可调度） |

**结论**：
- **瓶颈不是通道操作本身**（B1/B2 都是 II=1），**而是 token 串链形成的循环携带依赖**；
- **定案方案 (c)：并行 token 拓扑** —— 最小 II=1，stages 1..4 全部可行；
- 功能**不变**（testbench 3 个 case 全通过，含背压 case）；
- 附加收益：**RTL 寄存器 9 → 4 个**，规模 3812 → 2474 字节（**−35%**），
  端到端延迟反而**少 1 拍**；
- II 的表达方式定为**写进 IR**（`#[initiation_interval(1)]`，实测可用），
  生成的 `.ir` 自描述，不依赖 driver 参数。

> **同日追加（接口裁剪）**：Key/Response 通道改为 `flow_control=valid_data`
> （去掉 `key_out_rdy` 与 `rsp_in_rdy`），RTL 再降到 **2346 字节**，
> **II 与端到端延迟均不变**。关键回归结论：**stall 由 proc 内部流水控制实现，
> 与外部握手协议正交 —— 去掉 rdy 后"等 response"依然成立**。
> 代价是外部必须"随时可收/随时可返回"（见 P2 接口规范第 1 条）。

**给 A2 生成器的硬性要求**（详见定案文档 §5）：
1. 通道操作**不得串链**；
2. **前提条件必须校验**：同 proc 内通道操作的 predicate **互斥**。
   无法证明时必须退化为串行链（接受 II=2）并**显式报诊断** ——
   **静默拆链会产出"能编译、能过仿真、但真实硬件行为不确定"的 RTL**；
3. II 写进 IR；strictness 必填；节点名后缀 == `id=`；引用先于定义；
   按需选 `flow_control`（Key/Response 用 `valid_data` 走无背压）。

**交付**：`docs/A2-编排水法定案.md`、`scripts/ii_sweep.sh`、
主样本改造（并行 token + II 属性 + Key/Response 无背压）、对照样本 `*_serial_token.ir`、
`testcases/m0/ii_probe_parallel_tok.ir`、testbench（含 `result_out` 背压 case）。

**遗留**：多通道 / 多表在同一 proc 内的 II **未验证** —— **A3 首个检查点就该扫**。

### 内嵌 IR 静态校验器（A0 门禁）补全 proc/数组 state ✅（2026-09-17）

`scripts/xls_ir_lint.py` 原先只实现 `fn` 形态 —— 对真 XLS parser 完全接受的 proc IR 会报上千条
issue（demo9：8262 条），因此在流程里只能降级 WARN。现在按 `third_party/xls` 的**真实源码**逐条对齐：

- **补的语法**：新式 proc 签名（`<ch: T in|out>` + `init={...}` + `non_synth={...}`）、
  **数组 state** `bits[16][8]` 与任意层数组后缀（含 `(T,T)[3]`）、类型参数尾随 `id=/pos=[]`、
  `chan_interface`（含 5 类枚举合法性）、老式 `chan`（全套关键字 + 类型后必须有逗号 +
  仅 streaming 允许 fifo/bypass）、`proc_instantiation`、三引号多行字符串、`file_number`、
  `scheduled_*`（按花括号配对跳体，体内有内嵌 `source fn`）。
- **补的语义检查**（原来完全没有）：**先定义后引用**（`ir_parser.cc:461`）、
  **节点名 `.<N>` 后缀必须等于 op 名与 `id=N`**（`:1524/:1533`）、重名判据（Param/StateRead 豁免，`:1486`）、
  `state_element=` / `channel=` 的存在性、`init` 初值个数 == state 数（`:2285`）、
  `next_value` 的 `param`/`state_element` 二选一、重复关键字。
- **顺带修掉契约表缺陷**：`gen_op_contracts.py` 按 `to_snake(C++ 名)` 挂键，与 `op_list.h` 的 IR 名
  不总相等（`kNext` → IR 名是 `next_value`），导致 `next_value` 被补成**空契约**。
  现按 `op_list.h` 重映射（5 条：`next_value`/`smul`/`smulp`/`umul`/`umulp`）。
- **门禁可信度**：新增反向自测 `scripts/xls_ir_lint_selftest.py`（33 个错误用例 + 9 个正向控制）
  → **42/42 通过**；官方 XLS 全树 `.ir` → **768/768 通过**（A1 用真 XLS parser 测的是 745/768）；
  本仓库 `testcases/ir/**` → **25/25 通过**。
- **流程口径随之收紧**：`lint` 从"降级 WARN"恢复为**真门禁（报错即 FAIL）**。
- **发布形态修掉一个洞**：`p4xls lint-ir` 原先只在 cwd 有 `scripts/` 时可用；现在与 `flow` 共用
  "仓库 `scripts/` 优先 → jar 内嵌资源解到临时目录"的回退，并自带 `--contracts`
  → **单 jar + 空 root 也能跑 `lint-ir` 并正确拦截**。

**运维纪律（血的教训）**：**不要 kill 正在跑的 Bazel 构建。**
被 SIGTERM 的客户端会在 server 侧留下悬挂命令锁

此时 `kill -9` server 会让在飞动作作废 → 全量重编（实测 **22 分钟**）。
增量正常 10 秒 ~ 4 分钟。
