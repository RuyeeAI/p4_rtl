# A1 环境报告：在 macOS/arm64 上搭起可用的 XLS 验证环境

> 目标：把 A0 的「源码级静态校验」升级为「XLS 官方 parser 的真实判定」。
> 结论：**可行，但需要给 XLS 打两个补丁**，且本机网络环境有三个硬约束。

---

## 1. 先排除的路：没有现成的 macOS 产物

| 渠道 | 结果 |
|---|---|
| GitHub Release（google/xls） | 只有 **`xls-*-linux-x64.tar.gz`**（103.8MB），无 darwin/arm64 |
| conda `litex-hub` 频道 | 有 `xls`，但 **234 个文件全是 `linux-64`**，无 `osx-arm64` |
| conda-forge | 无 `xls` 包 |
| PyPI | `xls` 是 JS-XLS 的 Python 移植，**与本项目无关** |
| 容器（跑 linux 产物） | 本机 **无 docker / colima / podman / lima / nerdctl**，`qemu-x86_64` 也没有 |

**→ 只能从源码自建。**

---

## 2. 三个环境硬约束（都会让 Bazel 直接失败）

### 约束 A：GitHub 直连不可用，必须走镜像

```
https://github.com/...            → HTTP 000（连不上）
https://gh-proxy.com/https://github.com/...   → HTTP 200，约 40–75 KB/s
https://ghproxy.net/https://github.com/...    → HTTP 200
https://ghfast.top/https://github.com/...     → HTTP 200
https://bcr.bazel.build/          → HTTP 200 ✓（依赖元数据走这里，不受影响）
```

对策：
- bazelisk 二进制与 bazel 本体：`BAZELISK_BASE_URL` 指向 gh-proxy
- Bazel 的 module 源码归档：`config/bazel_downloader.cfg` 用 `rewrite` 把 `github.com/*` 改写到三个镜像（互备）

### 约束 B：本机有透明代理，Bazel 走它会 502

```
HTTP_PROXY=http://127.0.0.1:64321     ← WorkBuddy 注入
HTTPS_PROXY=http://127.0.0.1:64321
```

Bazel 的 Java HTTP 客户端会读这两个变量并走 CONNECT 隧道，而该代理**无法访问 github.com**，
表现为每个归档下载都失败于：

```
Unable to tunnel through proxy. Proxy returns "HTTP/1.1 502 Bad Gateway"
```

对策：`scripts/env.sh` 里的 `p4xls_bazel()` 包装函数**显式清空** `HTTP(S)_PROXY`/`ALL_PROXY` 再调用 bazelisk。
（实测绕开代理后 gh-proxy 与 bcr.bazel.build 均可直连。）

### 约束 C：bazelisk 默认按 "latest" 查 GCS，该域名不可达

```
https://www.googleapis.com/storage/v1/b/bazel/...  → 超时（HTTP 000）
```

现象：`could not resolve the version 'latest' to an actual version number`。
对策：`export USE_BAZEL_VERSION="$(cat third_party/xls/.bazelversion)"` → **8.7.0**，直接按
`BAZELISK_BASE_URL/8.7.0/bazel-8.7.0-darwin-arm64` 下载，绕过 GCS。

## 3. 核心：必须给 XLS 打「轻量依赖」补丁

### 问题：Bzlmod 是全图解析，跑 6 分钟只拉到 8.6MB

XLS 原版 `MODULE.bazel` 面向「全功能 XLS」，包含大量与 IR 解析/代码生成**毫无关系**的重依赖。
Bzlmod 的特点是：**只要某个 module 在依赖图里，Bazel 就必须拉它的源码才能读它的 BUILD 文件。**
于是哪怕只想编译 `//xls/ir:ir_parser`，也会被迫下载：

| 依赖 | 规模 | 谁需要 |
|---|---|---|
| **OpenROAD** | `git_override(init_submodules=True)`，含全部 submodule，GB 级 | EDA 集成，ir 链路不需要 |
| **LLVM 源码** | `llvm_raw_ext` → `@llvm-project`，GB 级且要编译数小时 | JIT / xlscc，ir 链路不需要 |
| **12 个 PDK** | SkyWater sky130 六变体 + ASAP7 三个，各 GB 级 | rules_hdl 的物理设计流程 |
| **Yosys / Icarus Verilog** | rules_hdl tools extension | 综合与仿真 |
| Perfetto / Verible / qt-bazel | 中大型 | 追踪 / 格式化 / OpenROAD GUI |
| Maven/JUnit、rules_android、rules_closure | 中型 | Perfetto 连带 |

实测：直连 GitHub 的 git clone 约 30KB/s，**6 分钟只拉到 8.6MB 就卡在 OpenROAD 上**。

### 依据：ir 闭包确实不需要它们

对 `xls/ir/BUILD`、`xls/common/BUILD`、`xls/codegen/BUILD` 逐项检索，
`org_theopenroadproject`、`rules_hdl`、`llvm-project`、`perfetto`、`verible` 的出现次数**均为 0**。

### 补丁一：替换 MODULE.bazel（45 → 30 个 bazel_dep）

`config/xls_MODULE.bazel.minimal` 摘掉 15 个依赖：

```
bant  fuzztest  hedron_compile_commands  llvm  openroad  rules_android
rules_bison  rules_closure  rules_flex  rules_hdl  rules_jvm_external
rules_m4  swig  tcl_lang  verible
```

两个细节：
- **`googletest` / `google_benchmark` 保留但去掉 `dev_dependency`** —— `xls/*/BUILD` 里有
  label 引用它们，整个删掉会让 Bazel 加载 BUILD 时报 `no repository visible as @googletest`。
- **`zlib-ng` / `zstd` 必须保留 `repo_name = "llvm_zlib" / "llvm_zstd"`** —— 省掉别名会与
  下面 extension 的 `use_repo(zstd_ext, "zstd")` 撞名，报
  `The repo name 'zstd' ... is already defined by a bazel_dep`。

同时保留 `z3` / `bitwuzla` / `ac_datatypes` / `zstd` 等 extension 的 `use_repo` 声明：
它们是**惰性生成**的，`use_repo` 只让名字可见，真正下载发生在有 target 引用时，
所以保留声明不带来下载成本，但能避免 BUILD 里的 label 解析失败。

### 补丁二：注释掉 `.bazelrc` 里引用 `@llvm-project` 的 Starlark flag

摘掉 LLVM 后，`.bazelrc:83` 这一行变成悬空引用：

```
build --@llvm-project//third-party:llvm_enable_zstd=false
```

这是 **Bazel 的 Starlark 命令行 flag 语法**（`--@repo//pkg:flag`）。Bazel 在**装配命令行
参数阶段**就要解析该 repo，找不到即报：

```
ERROR: @llvm-project//third-party:llvm_enable_zstd :: Error loading option
@llvm-project//third-party:llvm_enable_zstd: No repository visible as
'@llvm-project' from main repository.
```

**这个坑值得单独强调**：它
- 与「构建哪个 target」**完全无关** —— 哪怕构建一个零 XLS 依赖的空 `cc_binary` 也照样报；
- 报错信息里的 "Error loading option" 指**命令行选项**，不是 BUILD 里的 `select()` option，
  很容易被误导去翻 BUILD 文件（本报告作者就先后误判了三次：先怀疑 `xls/common/file/BUILD`，
  再怀疑 BCR 的 `zstd` module，再怀疑 stub repo）。

**定位方法**（可复用）：既然与 target 无关，就把 `MODULE.bazel` 砍到只剩 `module()` +
`bazel_dep(rules_cc)` 再构建。**如果极简依赖图仍报同一个错，就说明问题不在依赖图，
而在命令行/配置文件层面** —— 然后 `grep -nE '\-\-@' .bazelrc` 一击命中。

## 4. 补丁后实际下载的依赖

`external/` 下 35 个 repo，主力是：`protobuf+`(51M)、`abseil-cpp+`(15M)、
`rules_python+`(9.9M)、`rules_cc+`(3.9M)、`rules_java+`、`bazel_skylib+`、`re2`、`gtest`。
**没有任何 LLVM / OpenROAD / PDK 相关 repo。**

最终构建规模：**177 个包、9860 个 target、1986 个 action，耗时 9分28秒**（含依赖下载与编译）。

### 补丁三（额外）：`@rules_hdl` 最小存根

搞定前两个补丁后，分析阶段又暴露一处：`xls/build_rules/*.bzl` 有三处引用 `@rules_hdl`，
而 `xls/codegen/BUILD` 会 load `xls_build_defs.bzl`（串到 `xls_codegen_fdo_rules.bzl`）——
只要构建任何依赖 `//xls/codegen` 的目标（`//xls/ir:ir_parser` 就依赖
`//xls/codegen:module_signature`）就会失败。

**不能把真 `rules_hdl` 加回来**：它的 `MODULE.bazel` 依赖 openroad（git_override +
`init_submodules`，GB 级）、verilator、abc、tcl_lang、rules_7zip、readline、libffi、
bzip2、gperf…；而且它给 openroad 写的 `git_override` **在非 root module 下不生效**，
会直接导致版本解析失败。

**但被用到的只有**：`//pdk:build_defs.bzl` 的 `StandardCellInfo` provider，
以及 `//synthesis`、`//verilog` 下几个综合相关 rule —— 全部属于
「Bazel 规则驱动 codegen + 综合」路径，IR 解析校验**完全用不到**。

所以用 `xls_harness/rules_hdl_stub/` 提供一个最小 repo，
挂在 `config/xls_MODULE.bazel.minimal` 里：

```starlark
bazel_dep(name = "rules_hdl", version = "0.0.0")
local_path_override(module_name = "rules_hdl", path = "p4xls_harness/rules_hdl_stub")
```

存根只包含 `pdk/synthesis/verilog` 三个包，导出 `StandardCellInfo` provider 与几个空 rule。

## 5. 交付物与复现

### 新增文件

| 路径 | 作用 |
|---|---|
| `scripts/env.sh` | 环境变量：镜像、隔离目录、固定 bazel 版本、清代理的 `p4xls_bazel()` 包装 |
| `scripts/bootstrap_xls_env.sh` | 一键搭环境（下载 bazelisk → 拉 bazel → 打补丁 → 注入并构建） |
| `scripts/patch_xls_module.sh` | 打/还原 XLS 轻量补丁（MODULE.bazel + .bazelrc），含 `status` / `diff` |
| `scripts/setup_xls_harness.sh` | 把 `xls_harness/` 注入 XLS 源码树使其可被 Bazel 构建 |
| `scripts/xls_ir_verify.sh` | **统一入口**：构建并运行官方 parser 校验 |
| `config/xls_MODULE.bazel.minimal` | 轻量 MODULE.bazel |
| `config/bazel_downloader.cfg` | GitHub → 镜像的 rewrite 规则 |
| `xls_harness/ir_check_main.cc` | 官方 parser 驱动（支持整包/片段/round-trip/JSON） |
| `xls_harness/BUILD.bazel` | 对应 BUILD，含诊断用 `probe_minimal` |

### 复现命令

```bash
source scripts/env.sh
scripts/bootstrap_xls_env.sh          # 首次：下载 + 打补丁 + 构建
scripts/xls_ir_verify.sh testcases/ir # 之后：直接校验
```

### 设计取舍

- **bazelisk / bazel / 输出目录全部隔离在工程内 `.tools/`**，不污染 `~/.cache`，便于整套删除重来。
- **补丁可逆**：原文件备份为 `MODULE.bazel.orig` / `.bazelrc.orig`，`patch_xls_module.sh restore` 一键还原，
  便于与上游 diff 或将来跟随上游升级。
- **harness 用复制而非软链注入**：Bazel 对 workspace 内指向 workspace 之外的符号链接处理不一致。
- **harness 不用 `//xls/common/file:filesystem`**：该包 BUILD 的 `cc_test` 里有
  `@llvm-project//clang:builtin_headers_gen`，虽然测试不构建，但加载 BUILD 时也会解析 label。
  读文件改用标准库 `<fstream>`。
