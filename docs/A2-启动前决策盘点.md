### 关于 D3「双线并存」的落地含义（需要留意）

既然两条后端都要保留，就产生一个**维护面**：`../P4C`（Chisel 线）与 `p4_rtl`（XLS 线）
**共享 P4 前端 + IR 那 ~2,900 行**（Lexer / Parser / Ast / Ir / IrBuilder / Smt / Interp / Tools），
前端一旦有改动，两边要同步，否则会静默分叉。

三种缓解方式，按成本从低到高：

| 方式 | 做法 | 代价 |
|---|---|---|
| **① 定期对齐**（最低成本） | 以 `p4_rtl` 为前端改动的主战场，每隔一段时间把前端/IR 的改动同步回 `../P4C`，并在两边的日志里记下同步点（commit hash） | 靠纪律，有滞后风险 |
| **② 单向依赖** | `../P4C` 只保留 `ChiselBackend` + 一个薄 CLI，前端/IR 从 `p4_rtl` 以源码依赖或发布快照的方式引入 | 需要改造 P4C 的构建 |
| **③ 抽公共库** | 把前端 + IR 抽成独立模块，两个后端各自依赖 | 一次性改造最大，但之后最干净 |

**建议先做 ①**（零改造），并**立刻记一条基线**：在 `p4_rtl` 与 `../P4C` 的 memory 里
各写一条"当前共享代码的基线 commit"，作为将来同步的锚点。这条我现在就可以记。

> 补充：`p4_rtl` 的 fork 基线是 `../P4C` 的 `8c7eaaf`（2026-09-11），此后的改动尚未回流。

## 二、需要你决策（4 项）

### D1 起步方式：先做时序契约验证（M0）还是直接写 `XlsBackend`（A2）？

**背景**：方案里有两套编号 —— A 系列是工程步骤（A0 门禁 / A1 环境 / A2 写后端 / A3 表接口 / A4 组装 / A5 对拍），
M 系列是里程碑（M0 接口打样 / M1 全流程 / …）。两者不冲突，但**起步点不同**。

**待验证的核心问题**（方案里列为头号风险）：
XLS `proc.next(state)` 是**每拍迭代一次**的模型，而外部存储器有固定延迟（BRAM 1–2 拍、TCAM 3–4 拍）。
"`send key` → 等 L 拍 → `recv response` → 分发"这个闭环能不能在 XLS 里成立，**文档没有承诺**。

| 选项 | 做法 | 优点 | 风险 |
|---|---|---|---|
| **A. 先做 M0 打样** | 手工写一个最小 proc（固定头 parse→改字段→deparse + 一条 Key/Response 空壳通路），跑通 codegen + 仿真 | 用最小成本戳破最大的不确定性；不通则 M2 前提要重估，避免了在错误前提上写几千行生成器 | 多一个前置步骤 |
| **B. 直接写 A2** | 直接开发 `XlsBackend` 生成 proc 编排 | 少一步 | 若时序契约不成立，生成器要返工 |

**我的建议：A**。理由是这条风险**只能用实验回答、不能用阅读回答**，而 M0 的成本（1.5–2.5 人月里的一小部分）远低于返工。

### D2 面积/时序估算的精度要求：功能验证即可，还是需要真实工艺数据？

**背景**（A1 新发现）：XLS 的 `xls/estimators/{delay_model,area_model}` 会 load 工艺库数据
（SkyWater sky130、ASAP7），用于**逻辑努力延迟模型**与面积估算。A1 用**空存根**顶掉了它。

**影响面**：
- **功能正确性不受影响** —— codegen 照常出 Verilog
- **受影响的是**：XLS 的自动调度器按 delay model 决定流水深度，存根数据 → 流水深度估算不准
- 方案里 M4「基线评测」要的**面积/时序基线数据**，用存根会失真

| 选项 | 代价 | 适用 |
|---|---|---|
| **A. 继续用存根** | 0 | M0–M2 功能验证阶段 |
| **B. 引入真 PDK** | 下载 ASAP7 + SkyWater（GB 级），且需把 `@rules_hdl` 真依赖接回来 | M4 基线评测 / 任何要报面积时序的场合 |

**我的建议：现在用 A，到 M4 前再引入 B**。但需要你确认 **M4 的"基线评测"是否是本期的硬交付** ——
如果是，B 就是必做项，得提前排进计划（`@rules_hdl` 接回会连带 OpenROAD + PDK 下载，是笔不小的开销）。

## 三、A1 新获得的技术事实（降低了风险，不需决策）

| 发现 | 意义 |
|---|---|
| **LLVM 不是必需项** | `xls/ir`、`xls/common`、`xls/codegen`、`xls/interpreter` 的 BUILD 里 llvm 出现 **0 次**。`codegen_main`（出 Verilog）、`opt_main`（IR 优化）、`proc_interpreter`/`ir_interpreter`（解释执行）**都不需要 LLVM**。<br>只有 `xls/jit`（被 `eval_ir_main`/`eval_proc_main` 用作**加速求值**）需要它，那是 GB 级下载 + 数小时编译。 |
| **推论：A5 的 XLS 侧仿真可自建** | 基于 `proc_interpreter` 写一个自己的 eval main（形如已交付的 `ir_check_main`），**避开 LLVM**。接口已确认干净：`proc_interpreter` 只依赖 `//xls/ir:*` + absl。 |
| **PDK 数据只被 load、从未被调用** | `for_each_sky130_cells` / `for_each_asap7_cells` 在 `delay_model`/`area_model` 的 BUILD 里只有 `load`，没有调用点 → 空存根足够（已实现）。 |
| **proc/concat/channel 语法已被官方 parser 接受** | 25 个 P4C 样本 25/25 通过且 round-trip 逐字节稳定；官方 proc 样本 4/4 通过。 |
| **Verilog 生成核心干净，但官方 `codegen_main` 不干净** | 实测 `//xls/tools:codegen_main` 会沿依赖链拉到 `@at_clifford_yosys`（Yosys，FDO 反馈驱动优化用）与 `delay_model`。但核心 target `//xls/codegen:{codegen_pass_pipeline, pipeline_generator, verilog_conversion}` 的依赖**全部干净**（llvm/yosys/synthesis 出现 0 次）。<br>→ **A2 的产出一侧应自建最小驱动**（形如已交付的 `ir_check_main`），只链接 `//xls/codegen:*` 核心，绕开 yosys / LLVM / delay_model 全套。 |

**这条"越往前推、越撞重依赖"的现象值得记一笔**：`ir_parser` → 干净；`xls/codegen` 核心 → 干净；
但 `xls/tools/*` 这些**面向用户的完整工具**会为了 FDO / 综合 / 可视化把 Yosys、LLVM、OpenROAD 全拉进来。
**对策是一致的：不碰 `//xls/tools`，自己写最小驱动。** 这是 A1 已验证有效的模式。
