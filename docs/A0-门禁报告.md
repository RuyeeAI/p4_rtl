# A0 门禁报告：P4C 产出的 IR 能否被 XLS 接受

**日期**：2026-09-15
**结论**：✅ **通过**。P4C 生成的 XLS IR 文本语法正确，唯一不兼容点已修复。
**范围**：11 个 demo P4 程序 → 25 个 `.ir` 文件 → 25/25 通过语法校验。

---

## 1. 门禁为什么必做

方案里的整条路线是：

```
P4C（前端/中端）→ XLS IR 文本 → [A2: 补 proc 编排] → XLS codegen → Verilog
```

**P4C 的 `IrText` 是自己写的 IR 文本发射器**，并非调用 XLS 官方 API 生成。
因此"语法是否被 XLS 的 parser 接受"必须实测——这是路线成立的前提。
若此处不成立，后面 A2–A5 全部作废。

## 3. 唯一的不兼容点与修复

### 问题

P4C 生成：

```text
n7: bits[16] = array_index(reg_portBytes, n6)
```

XLS 要求：

```text
n7: bits[16] = array_index(reg_portBytes, indices=[n6])
```

### 证据链（源码级）

**证据 1** —— `../third_party/xls/xls/ir/ir_parser.cc:1065-1073`：

```cpp
case Op::kArrayIndex: {
  std::vector<BValue>* index_args =
      arg_parser.AddKeywordArg<std::vector<BValue>>("indices");
  std::optional<bool>* assumed_in_bounds =
      arg_parser.AddOptionalKeywordArg<bool>("assumed_in_bounds");
  XLS_ASSIGN_OR_RETURN(operands, arg_parser.Run(/*arity=*/1));
```

**证据 2** —— `ir_parser.cc:329-376` 的 `ArgParser::Run`：

```cpp
absl::StatusOr<std::vector<BValue>> Run(int64_t arity) {
  ...
  if (parser_->scanner_.PeekNthTokenIs(1, LexicalTokenType::kEquals)) {
    // Found `XXXX=...` which means that operands are complete and
    // keyword arguments have begun.
    break;
  }
  ...
  if (arity != kVariadic && operands.size() != arity) {
    return absl::InvalidArgumentError(...);   // ← 位置写法在此被拒
  }
```

位置参数与关键字参数**分开解析**，`arity=1` 而 `indices` 是 mandatory keyword。
因此 `array_index(arr, idx)` 会同时触发 `arity` 不匹配与 `indices` 缺失两个错误。

**证据 3** —— XLS 官方测试与测试数据一致使用关键字形式：

```text
xls/ir/testdata/ir_parser_round_trip_test_ParseArrayIndex.ir:
  ret array_index.2: bits[32] = array_index(x, indices=[literal.1], id=2)

xls/ir/testdata/ir_parser_round_trip_test_ParseNestedBitsArrayIndex.ir:
  ret array_index.1: bits[2][5] = array_index(p, indices=[q, r], id=1)
```

### 修复

`src/main/scala/P4C/IrText.scala` 三处：

| 位置 | 改动 |
|---|---|
| `:128`（生成） | `array_index(${regParamOf(inst)}, ${ref(idx)})` → `array_index(${regParamOf(inst)}, indices=[${ref(idx)}])` |
| `:304`（解析） | 索引来源从位置参数 `pos(1)` 改为正则提取 `indices=[(\w+)]` |
| `:20` / `:33`（文档） | 示例与节点映射说明同步更新 |

**验证**：修复后重新生成全部 demo，`grep array_index` 确认为 `indices=[...]` 形式。

## 4. 已确认兼容的语法点

逐项对照 XLS parser 源码核对，全部兼容：

| P4C 生成 | XLS 规则来源 | 结论 |
|---|---|---|
| `// p4c-*` 头部注释 | `ir_scanner.cc:156-166` `DropEndOfLineComment()`，在 `NextToken` 循环中与空白一起跳过 | ✅ |
| `package Demo9L3forwarder` | `ir_parser.h:445` `ParsePackageName()` | ✅ |
| 一个文件多个 `fn` | `ir_parser.h:469-477`，顶层循环接受 fn/proc/block/chan/file_number | ✅ |
| `fn f(a: bits[8], b: bits[16]) -> (bits[16], bits[8]) {` | `ir_parser.cc:2160-2167` `ParseFunctionSignature`：`->` 后走 `ParseType` → `ParseTupleType` | ✅ |
| `n0: bits[16] = literal(value=2)` | op 契约：`literal` arity=0, mandatory `value` | ✅ |
| `ret sinks: (T,...) = tuple(...)` | `ir_parser_test.cc:108` 官方样本 `ret literal.1: (bits[16], bits[96]) = literal(...)` | ✅ |
| `sel(cond, cases=[a, b])`（无 default） | op 契约：`sel` arity=1, `cases` mandatory, `default` optional；官方 `.ir` 多处无 default | ✅ |
| `zero_ext(x, new_bit_count=8)` | `ir_parser.cc` `case Op::kZeroExt:`（与 `kSignExt` 共享），`new_bit_count` mandatory | ✅ |
| `bit_slice(x, start=4, width=2)` | op 契约：arity=1, `start`/`width` mandatory | ✅ |
| `bits[16][8]`（数组类型） | `ParseType` → `bits[N]` 后接 `[M]` 维度 | ✅ |

## 5. 校验器与可信度

真实 XLS parser 需要构建 XLS（Bazel 8.7.0，数小时 + 依赖下载；
本轮 `brew install bazelisk` 被沙箱拦截，见 §7）。

因此本轮采用**源码级静态校验器**作为代理验证：

- `scripts/gen_op_contracts.py` —— 从 `ir_parser.cc` **自动提取** 84 条 op 参数契约
  （arity / mandatory keywords / optional keywords），产出 `config/op_contracts.json`
- `scripts/xls_ir_lint.py` —— 复现 XLS 的词法与结构规则：
  - token 集与关键字集取自 `ir_scanner.h` 的 `LexicalTokenType` / `Token::GetKeywords()`
  - 注释规则取自 `ir_scanner.cc`
  - 顶层结构取自 `ir_parser.h` 的 `ParseDerivedPackageNoVerify`
  - 逐 op 校验 arity 与关键字参数

### 可信度回归

用 **XLS 仓库自带的 768 个 `.ir`** 做正样本回归（这些必然能被真实 parser 接受）：

| 范围 | 通过率 |
|---|---|
| 全部 768 个 | 518 / 768（受 proc/block/channel 等 P4C 不生成的语法干扰） |
| **纯 `fn` 子集 493 个** | **468 / 493 = 94.9%** |

剩余 25 个失败均在 XLS 边缘语法（`token` 字面量、FFI 内嵌换行、数组类型字面量等），
**P4C 均不生成**。校验器对 P4C 实际用到的 12 个 op 与语法子集是充分覆盖的。

## 6. 对方案的影响

**没有影响，路线成立。** 且修复代价极小（3 处代码，约 10 行）。

需要留意的两点：

1. **改动落在了 P4C 的 `IrText` 上**，而 `IrText.parse` 也在用（round-trip）。
   解析侧已同步修改，但**建议补一个 round-trip 回归测试**（dump∘parse∘dump 逐字节稳定是原设计承诺）。
2. **`array_index` 之外，P4C 尚未生成 `proc`/通道**。A0 只验证了"`fn` 形态的 IR 合法"，
   **`proc` 编排（A2）的语法正确性尚未覆盖**——这是 A2 开始时的第一个检查点。

**建议**（需在沙箱外执行）：

```bash

cd ../third_party/xls
```
