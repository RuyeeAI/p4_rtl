## 1. 为什么需要这份文档

两条线**共享约 2,900 行 P4 前端 + IR**：

```
Lexer / Parser / Ast / Directive      ← P4 前端
Ir / IrBuilder / Signature            ← 中间表示
IrText                                ← XLS IR 文本 dump/parse（对齐实验产物）
Smt / Interp / Tools                  ← 形式化 / 解释器 / 工具
```

这部分一旦在一边被改动、另一边不知道，就会**静默分叉**：两边都能编译、测试都过，
但语义已经不同，将来合并时会变成一场考古。

## 4. 对齐流程（「定期对齐」方式）

选定的是成本最低的方案：**以 `p4_rtl` 为前端改动的主战场，定期把共享代码的改动回流到 `P4C`。**

**做法**：

1. **在 `p4_rtl` 里改前端/IR**（正常提交，`docs/`、`scripts/` 等 XLS 专属内容不算共享）。
2. **每隔一段时间**（或某块前端工作告一段落时）执行上面的对比命令，列出分叉文件。
3. **逐个判断**该改动是否对 Chisel 线有意义：
   - 有意义（如 P4 语法特性补全、IR 语义修正）→ 回流到 `P4C`
   - 无意义（如 `IrText` 的 XLS 格式修复）→ 记录在本文第 3 节，不回灌
4. 回流后在两边各记一条 commit hash 作为新锚点。

**为什么不做「单向依赖」或「抽公共库」**：那两种方式改造量大，
而当前前端改动频率不高（A2 的工作重心在生成器，不在前端），
先按最低成本方式走，等前端改动变频繁再升级——**本文第 3 节的清单就是这个决策的触发器**：
一旦分叉文件超过 3 个，就该考虑抽公共库了。
